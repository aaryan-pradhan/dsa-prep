Number Theory & Bits

Arithmetic problems where the answer is a formula plus a counting trick: cancel pairs, reduce modulo a prime, flip "divisors of i" into "multiples of d", or count each bit's contribution instead of each number. Reach for this page when n or a value goes past 10⁶ and a loop over it is hopeless.

Recognition rules

The judgment calls that separate these problems from each other.

1

Swap "for each i, its divisors" for "for each d, its multiples". The harmonic sum ∑ X/d = O(X log X). See Counting Divisors, Common Divisors, and Sum of Divisors (∑σ(i) = ∑ d·⌊n/d⌋).

2

When n reaches 10¹²–10¹⁵, count contributions, not numbers: per bit position (Counting Bits), or per block of equal ⌊n/d⌋ (Sum of Divisors).

3

An exponent of 10⁹ or more means square-and-multiply in O(log b). See Exponentiation, Exponentiation II, and the inverse of 2 in Sum of Divisors (mpow(b, MOD−2)).

4

A product of two values near 10⁹ or larger must be shrunk first: divide before multiplying (a / gcd * b in Next Common Height), or reduce both operands mod p (mmul in Sum of Divisors).

5

When the answer is the one thing that doesn't cancel, fold everything into one accumulator and store nothing. Missing Number uses XOR pairs. Weird Algorithm uses a plain state loop, with the terminal value printed outside it.

1 · Simulation & bits

No clever structure, just a scalar accumulator. Sometimes the process really is short (Collatz). Sometimes it isn't, and each bit is counted as a periodic pattern.

Weird Algorithm

O(steps)
The ask
Print n, then apply n → n/2 if even and n → 3n+1 if odd, printing each value until 1.
nₖ₊₁ = nₖ/2 (even), 3nₖ+1 (odd); stop at 1
Key observations
  1. There is no aggregate to compute, so print every state.
  2. 1 can't enter the transform (1 → 4 → 2 → 1 loops), so print it after the loop.
  3. With n ≤ 10⁶, the longest run is 524 steps (from 837799). The values peak at 56 991 483 520 (from 704511), which overflows int.
Brute force → why it dies
naiveSimulate.
costO(steps) ≤ 524.
dies atNothing on time. int dies at the 5.7·10¹⁰ peak.
thereforeThe simulation is the solution. Only the type matters: long long.
Implementation

The loop is while (n != 1): print, then transform. The final 1 prints outside the loop, which also makes input 1 correct with no special case.

math/Weird_Algorithm.cppverbatim
// Problem: Weird Algorithm (Collatz sequence)
// Link: CSES 1068
// Pattern: simulate with a loop, print each state, exit right after the terminal value
// Time: O(steps) per input, steps bounded by known Collatz behavior for n <= 1e6
// Space: O(1)
//
// n even -> n/2, n odd -> 3n+1, repeat until n == 1. Print every value n
// takes, including the initial n and the final 1.
//
// Example:
//     3 -> 3 10 5 16 8 4 2 1

#include <iostream>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    long long n;
    cin >> n;

    while (n != 1) {
        cout << n << ' ';
        if (n % 2 == 0) n /= 2;
        else n = 3 * n + 1;
    }
    cout << 1 << '\n';

    return 0;
}
Gotchalong long is required, not just cheap. This file's Recall Trail says 3n+1 never overflows int for n ≤ 10⁶, but starting from 704511 the sequence reaches 56 991 483 520.
Recognize"print every value of a process until it hits a fixed state" → while loop, terminal value printed outside.

Missing Number

O(n)
The ask
The numbers 1..n are given with one missing, in any order. Find the missing one.
x = (1 ⊕ 2 ⊕ … ⊕ n) ⊕ (a₁ ⊕ … ⊕ aₙ₋₁)
Key observations
  1. v ⊕ v = 0, and XOR is commutative, so order is irrelevant.
  2. Every present value appears twice and cancels. Only the missing one survives.
  3. Fold each value in as it is read, with no array.
Brute force → why it dies
naiveSort, or use a seen[] array, and scan for the gap.
costO(n log n) time or O(n) memory.
dies atIt passes at n ≤ 2·10⁵. It only loses on memory and code length.
thereforeXOR accumulator: O(n) time, O(1) space.
Diagram
Implementation

The first loop XORs 1..n. The second XORs the n−1 inputs as they are read. x is long long, which isn't needed because XOR never exceeds 2¹⁸.

math/Missing_Number.cppverbatim
// Problem: Missing Number
// Link: CSES 1083
// Pattern: XOR 1..n with the given values — duplicates cancel, only the missing one survives
// Time: O(n)  Space: O(1)
//
// Given n and n-1 distinct values from 1..n, find the missing one.
//
// Example:
//     n=5, [2 3 1 5] -> 4

#include <iostream>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    long long x = 0;
    for (int i = 1; i <= n; i++) x ^= i;

    int v;
    for (int i = 0; i < n - 1; i++) {
        cin >> v;
        x ^= v;
    }

    cout << x << '\n';
    return 0;
}
GotchaRead exactly n−1 values. The sum alternative n(n+1)/2 − ∑ needs long long, and XOR sidesteps that entirely.
Recognize"everything appears in pairs except one" → XOR everything together.

Counting Bits

O(log n)
The ask
Total the one bits over all integers 1..n, with n ≤ 10¹⁵.
for bit i, B = 2ⁱ⁺¹: (n div B)·B/2 + max(0, n mod B − B/2 + 1)
Key observations
  1. Counting from 0, bit i has period 2ⁱ⁺¹: 2ⁱ zeros, then 2ⁱ ones.
  2. Full periods in 0..n contribute (n div B)·B/2.
  3. The partial tail has length (n mod B)+1, and its ones start at offset B/2.
  4. n ≤ 10¹⁵ needs about 50 bits, so there are 50 terms.
Brute force → why it dies
naive∑ __builtin_popcountll(i).
costO(n)
dies atn ≤ 10¹⁵ → 10¹⁵ iterations.
thereforeCount per bit position: O(log n).
Diagram
Implementation

The loop runs while (1LL << i) <= n, so only bits that can be set are counted. It counts over 0..n, and 0 adds nothing. The commented-out popcount loop above it is the brute force.

2 · GCD / LCM

Two periodic events line up every lcm steps. Euclid gives the gcd in O(log), and lcm = a / gcd · b keeps the product small.

Next Common Height

O(log min(a,b))
The ask
Both climbers start at x. One climbs a per move, the other b per move. Find the next height above x that both reach.
x + lcm(a, b), lcm = a / gcd(a, b) · b
Key observations
  1. A shared height is x + k·a = x + m·b, so the offset is a common multiple.
  2. The smallest positive common multiple is lcm(a, b).
  3. gcd by Euclid: a %= b; swap until b = 0.
Brute force → why it dies
naiveStep h = x + a, x + 2a, … until (h − x) mod b = 0.
costO(b / gcd) per test.
dies atCoprime a, b near 10⁹ → 10⁹ steps per test.
thereforeClosed form via gcd: O(log min(a, b)).
Diagram
Implementation

This is a hand-written iterative gcd, not std::gcd. The one line that matters is a / gcd(a, b) * b: divide first.

math/Next_Common_Height.cppverbatim
// Problem: Next Common Height (Nandu and Chandu)
// Pattern: LCM of two step sizes — divide-before-multiply to avoid overflow
// Time: O(log(min(a,b))) per test case  Space: O(1)
//
// Both start at height x. One jumps up by a each move, the other by b each
// move. T test cases, each (x, a, b). Output the next height (strictly above
// x) both will visit.
//
// Example:
//     (1, 1, 2)  -> 3
//         (1, 19, 19) -> 20
//         (17, 2, 3) -> 23

#include <iostream>
using namespace std;

long long gcd(long long a, long long b) {
    while (b) {
        a %= b;
        swap(a, b);
    }
    return a;
}

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int t; cin >> t;
    while (t--) {
        long long x, a, b;
        cin >> x >> a >> b;
        long long lcm = a / gcd(a, b) * b;
        cout << x + lcm << '\n';
    }
    return 0;
}
Gotchaa * b / gcd can overflow long long even when the lcm itself fits. Divide before multiplying.
Recognize"two periodic things, when do they next coincide" → lcm.

3 · Modular exponentiation

Square the base and halve the exponent each round, multiplying the base into the result when the low bit is set. For a tower of powers mod a prime p, reduce the upper exponent mod p−1.

Exponentiation

O(n log b)
The ask
Answer n queries of ab mod 10⁹+7, with a, b ≤ 10⁹.
a^b = (a²)^⌊b/2⌋ · a^(b mod 2)
Key observations
  1. b in binary picks which of a, a², a⁴, a⁸, … to multiply together.
  2. Each is the square of the previous one, so a loop of about 30 rounds suffices.
  3. Operands are < p ≈ 10⁹, so each product is < 10¹⁸ and fits ll.
Brute force → why it dies
naiveMultiply by a, b times.
costO(b) per query.
dies atb = 10⁹, n = 2·10⁵ → 2·10¹⁴.
thereforeBinary exponentiation: O(log b) per query.
Diagram
Implementation

mmul does (a*b) % MOD without reducing the operands first. That is safe here only because every input a is ≤ 10⁹ < MOD. This file has no pasted statement block (CSES 1095).

Exponentiation II

O(n log p)
The ask
Compute abc mod p, with p = 10⁹+7 and 00 = 1.
a^(b^c) ≡ a^(b^c mod (p−1)) (mod p) for p ∤ a
Key observations
  1. Fermat: ap−1 ≡ 1 when p ∤ a, so exponents live mod p−1.
  2. The inner power is mpow(b, c, p−1), the same function with a different modulus.
  3. a ≤ 10⁹ < p, so p ∣ a only when a = 0. Handle a = 0 by hand.
  4. 0bc is 1 exactly when bc = 0, which means b = 0 and c ≥ 1.
Brute force → why it dies
naiveCompute bc exactly, then athat.
costbc has up to 30·10⁹ bits.
dies atb, c ≤ 10⁹: it can't even be stored.
thereforeReduce the exponent mod p−1, then use two fast pows: O(log p).
Diagram
Implementation

mmul and mpow take a default mod = MOD parameter, so one pair serves both levels. The two zero guards run before Fermat is applied. Case a = 0, b = 0, c = 0 gives bc = 1, so 01 = 0.

4 · Divisors & multiples

Every divisor question can be turned around: instead of asking what divides i, ask which multiples each d reaches. Loop d over its multiples in O(X log X) total. For n up to 10¹², group the d with equal ⌊n/d⌋.

Counting Divisors

O(X log X + n)
The ask
Given up to 10⁵ numbers x ≤ 10⁶, print τ(x), the number of divisors of each.
τ(x) = |{ i : i | x }|; for i: for j = i, 2i, …: d[j]++
Key observations
  1. i divides j ⇔ j is a multiple of i, so each i adds 1 to all its multiples.
  2. ∑i≤X X/i ≈ X ln X ≈ 1.4·10⁷ for X = 10⁶.
  3. Precompute once, then each query is a lookup.
Brute force → why it dies
naiveTrial division up to √x for each query.
costO(n√X)
dies atn = 10⁵, X = 10⁶ → 10⁸ modulo operations. That is borderline at 1 s.
thereforeHarmonic sieve: O(X log X) once, O(1) per query.
Diagram
Implementation

pre() runs once after reading t. d is a global ll[1000001], which is 8 MB, zero-initialised, and off the stack. The commented-out solve is the √x brute force.

Common Divisors

O(X log X)
The ask
Find the largest gcd over all pairs in the array.
max { g : |{ i : g | xᵢ }| ≥ 2 }
Key observations
  1. If g divides two elements, their gcd is ≥ g. So the answer is the largest g dividing at least two elements.
  2. Count the multiples of g present using a frequency array: ∑ freq[g·k].
  3. Try g from max down and stop at the first count ≥ 2. The whole scan is still harmonic, O(X log X).
Brute force → why it dies
naivegcd of every pair.
costO(n² log X)
dies atn = 2·10⁵ → 2·10¹⁰ pairs.
thereforeIterate over the answer g and count multiples: O(X log X), X = 10⁶.
Diagram
Implementation

freq is sized to the actual max, not 10⁶. The downward loop returns on the first hit. g = 1 always has cnt = n ≥ 2, so the loop always prints.

Sum of Divisors

O(√n log p)
The ask
Compute ∑i=1n σ(i) mod 10⁹+7, with n ≤ 10¹².
∑ σ(i) = ∑d=1n d·⌊n/d⌋ block [l, r] with v = ⌊n/l⌋, r = ⌊n/v⌋: v · (l+r)(r−l+1)/2
Key observations
  1. d is a divisor of exactly ⌊n/d⌋ numbers ≤ n, and contributes d to each of them.
  2. ⌊n/d⌋ takes at most 2√n distinct values, so group d into blocks.
  3. Within a block, ∑ d is an arithmetic series.
  4. The series needs /2, and after reducing mod p that means multiplying by the inverse of 2.
Brute force → why it dies
naive∑d d·⌊n/d⌋ one d at a time, or a σ sieve.
costO(n)
dies atn = 10¹² → 10¹² iterations.
thereforeQuotient blocks: O(√n) ≈ 2·10⁶ blocks.
Diagram
Implementation

Every helper reduces its operands before combining them, which is needed because l and r reach 10¹². mdiv(…, 2) multiplies by mpow(2, MOD−2). l = r + 1 jumps to the next block.
