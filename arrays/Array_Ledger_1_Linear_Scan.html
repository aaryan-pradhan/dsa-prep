The Ledger · Arrays

Linear Scan & Frequency

Every problem here is answered by walking the array once (or once after a sort) while carrying a tiny amount of state — a scalar, a pos[] table, a frequency map, a stack. No windows, no two pointers, no binary search. Reach for this page when the answer is a count or an extremum over a sequence and nothing about the problem forces you to revisit an element you have already passed.

Recognition rules

The judgment calls that separate these problems from each other. Every rule must be demonstrated by at least two entries on this page.

1

Fix the right endpoint and the problem collapses to one carried scalar. Maximum Subarray Sum carries the best sum ending at j, Maximum Difference carries min(a[0..j−1]), Increasing Array carries the running floor. In all three the recurrence is one line and the seed is where the bugs live.

2

A neutral seed (0) is only safe when the empty answer is legal. Maximum Subarray Sum must seed cur = best = x[0] because the subarray is nonempty; Maximum Difference must start the loop at i=1 with minSoFar = arr[0] so index 0 cannot pair with itself. Both bugs are invisible until the input is all-negative or strictly decreasing — the wrong version returns 0.

3

Splitting by parity gives classes that never interact, so the only thing left is the junction between them. Beautiful Permutation gets every within-half gap ≥ 2 for free and checks exactly one boundary; Parity Constrained Sort sorts each class and ignores cross-class inversions because they are unfixable. Solve each class trivially, then handle the single interaction.

4

When the answer is a sum of independent per-index indicators, maintain it instead of recomputing it. Collecting Numbers computes 1 + ∑[pos[i] < pos[i−1]] once; Collecting Numbers II keeps that same sum alive by touching only the ≤4 indicators a swap can flip — subtract each one's old value before the swap, add its new value after.

5

unordered_set/unordered_map on plain integer keys is CSES-unsafe: an anti-hash test forces every key into one bucket. Distinct Values TLE'd exactly this way and moved to sort + adjacent-run scan; Distinct Subsequences uses std::map for its frequency table for the same reason. Comparison-based structures cannot be attacked by input.

6

Ask "does contiguity matter?" before choosing the technique — the titles will not tell you. Maximum Subarray Sum is meaningless without contiguity (Kadane); Distinct Subsequences is pure per-value combinatorics because contiguity is irrelevant (Π(f+1)−1); Distinct Values ignores position entirely. Three problems about "runs of elements", three unrelated shapes.

1 · Single-pass running state

One left-to-right pass, one or two scalars carried forward, O(1) extra space. The recurrence is never the hard part — picking which running value is sufficient, and seeding it so the degenerate input still answers correctly, is the whole problem.

Maximum Subarray Sum

O(n)
The ask
Given x[0..n−1], find the largest sum of a contiguous, non-empty block. Values may be negative.
maximise ∑ₖ₀ₕₖₒₖ xₖ over 0 ≤ i ≤ j < n
Key observations
  1. Every subarray ends somewhere. Fix the right end j and the problem splits into n independent questions: best sum ending at j.
  2. That best either extends the previous one or starts fresh at j: cur = max(xₕ, cur + xₕ). Nothing else is worth considering.
  3. Equivalently: a running sum that has gone negative is dead weight — dropping it can only help.
  4. The winning block need not end at n−1, so best is a separate max over the whole cur sequence.
  5. "Non-empty" is load-bearing: the seed must be x[0], never 0.
Brute force → why it dies
naiveEnumerate every (i, j) pair and sum the block; prefix sums remove the inner summation but not the pair enumeration.
cost O(n³) raw, O(n²) with prefix sums.
dies at n ≤ 2·10⁵ → 2·10¹⁰ pairs. The sum itself reaches 2·10¹⁴ (n·|x|), past int.
therefore Carry the best-ending-here sum in one long long scalar and take a running max — O(n) time, O(1) state.
Diagram
Implementation

The array is read into a vector first purely so that x[0] can seed both scalars before the loop starts at i=1; the algorithm itself never looks back. The line to read carefully is cur = max(x[i], cur + x[i]) — the first argument is the restart branch, and it is what makes a negative prefix impossible to carry forward.

arrays/Maximum_Subarray_Sum.cppverbatim
// Problem: Maximum Subarray Sum
// Link: CSES 1643
// Pattern: Kadane's — running best-ending-here, extend or restart at each element
// Time: O(n)  Space: O(1)
//
// Max sum of a contiguous nonempty subarray.
//
// Example:
//     -1 3 -2 5 3 -5 2 2 -> 9   (subarray [3, -2, 5, 3])

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    vector<long long> x(n);
    for (int i = 0; i < n; i++) cin >> x[i];

    long long cur = x[0], best = x[0];
    for (int i = 1; i < n; i++) {
        cur = max(x[i], cur + x[i]);
        best = max(best, cur);
    }

    cout << best << '\n';
    return 0;
}
GotchaSeed both cur and best with x[0], not 0 — the subarray must be non-empty, so an all-negative array must return its least-negative single element. best must be tracked separately from cur: the optimal block rarely ends at the last index.
Recognize"maximum sum of a contiguous block" → extend-or-restart running sum, running max kept alongside.

Maximum Difference

O(n)
The ask
Pick two indices with i < j maximising arr[j] − arr[i]. Report that difference (it may be negative).
maximise arr[j] − arr[i] subject to i < j
Key observations
  1. This is not global max − global min: the ordering constraint can forbid that pair. [5,1] has only one legal pair, worth −4.
  2. Fix j. The best partner is the smallest element strictly before it — a prefix minimum, free to carry.
  3. So the answer is maxₕ (arr[j] − minSoFarₕ), one pass, one scalar.
  4. Order inside the loop matters: score arr[i] against minSoFar before folding arr[i] into it, or an index pairs with itself.
  5. No clamp to 0. A strictly decreasing array has a negative answer, and that is the correct least-bad legal pair.
Brute force → why it dies
naiveFor each j, scan every i < j and keep the best difference.
cost O(n²) — n(n−1)/2 pairs.
dies atNo bound is stated in the file, but at array-problem scale n = 10⁵ that is 5·10⁹ comparisons — seconds to minutes.
therefore Replace the inner scan with one prefix-minimum scalar — O(n) time, O(1) state.
Diagram
Implementation

Two lines in the loop body, and their order is the algorithm: maxDiff is updated first, so minSoFar at that moment still describes arr[0..i−1] only. The seeds do the same job from outside the loop — minSoFar = arr[0] and maxDiff = arr[1] − arr[0] mean the pass begins at i=1 with one real pair already scored, so index 0 is never allowed to pair with itself.

arrays/Maximum_Difference.cppverbatim
// Problem: Maximum Difference
// Pattern: single pass, running min — max(arr[j] - min_so_far) over i < j
// Time: O(N)  Space: O(1)
//
// Given N elements in an array, select two indexes i and j such that i < j
// and arr[j] - arr[i] is maximum possible. Output that maximum difference.
//
// Example:
//     [1,2,3,4,5] -> 4   (i=0, j=4: 5-1=4)

#include <iostream>
#include <vector>
using namespace std;

int maxDifference(vector<int>& arr) {
    int minSoFar = arr[0];
    int maxDiff = arr[1] - arr[0];

    for (int i = 1; i < (int)arr.size(); i++) {
        maxDiff = max(maxDiff, arr[i] - minSoFar);
        minSoFar = min(minSoFar, arr[i]);
    }

    return maxDiff;
}

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n; cin >> n;
    vector<int> arr(n);
    for (int i = 0; i < n; i++) cin >> arr[i];

    cout << maxDifference(arr) << "\n";
    return 0;
}
GotchaNot "global max − global min" — that silently ignores i < j. And starting the loop at i=0 with minSoFar already arr[0] lets index 0 pair with itself for a free 0, which inflates the answer above every legal pair on a decreasing array.
Recognize"best pair under an ordering constraint i < j" → running extremum of the prefix, scored before it is updated.

Increasing Array

O(n)
The ask
Given a[0..n−1], the only legal move is to raise one element by 1. Find the least number of moves that makes the array non-decreasing.
minimise ∑ (bᵢ − aᵢ) subject to bᵢ ≥ aᵢ and bᵢ ≥ bᵢ₋₁
Key observations
  1. You may only raise, never lower — so bᵢ ≥ aᵢ is forced and the answer is a sum of non-negative shortfalls.
  2. Raising bᵢ above max(aᵢ, bᵢ₋₁) never helps: it costs more now and only raises the floor for later elements. So bᵢ = max(aᵢ, bᵢ₋₁) is optimal.
  3. That makes the choice at each index independent of everything after it — one left-to-right pass, no lookahead, no DP.
  4. The comparison is against the adjusted previous value, not the original aᵢ₋₁. A bump propagates.
Brute force → why it dies
naiveSearch over target arrays b, or re-scan the prefix at each index to find the running maximum.
cost O(n²) for the re-scan; unbounded for the search.
dies at n ≤ 2·10⁵ → 4·10¹⁰ operations. Also ∑(prev − x) reaches ~2·10¹⁴, past int.
therefore Carry the running maximum in a single scalar. No structure needed at all — O(n) time, O(1) space, accumulator in long long.
Diagram
Implementation

prev is the floor and is only ever assigned in the else branch — when a shortfall is paid the element becomes prev conceptually, so leaving prev alone is exactly right. Reading and processing in the same loop keeps space at O(1): the array is never stored.

arrays/Increasing_Array.cppverbatim
// Problem: Increasing Array
// Link: CSES 1094
// Pattern: single-pass greedy — track running previous (post-adjustment), pay the shortfall
// Time: O(n)  Space: O(1)
//
// Only allowed move: increase any element by 1. Minimum total moves to make
// the array non-decreasing.
//
// Example:
//     3 2 5 1 7 -> 5

#include <iostream>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    long long prev = 0, cost = 0;
    for (int i = 0; i < n; i++) {
        long long x;
        cin >> x;
        if (x < prev) cost += prev - x;
        else prev = x;
    }

    cout << cost << '\n';
    return 0;
}
GotchaCompare against the running prev, not a[i-1]. A bump raises the floor for everything after it, and the two differ the moment two dips occur in a row. cost must be long long.
Recognize"one-directional edit only, minimum total change to make a sequence monotone" → single-pass running floor, pay the shortfall.

2 · Parity-based construction

Split the values by parity and the two classes stop interacting: within a class every pair differs by at least 2, and nothing can cross between classes. What is left is one boundary to check (Beautiful Permutation) or one sort per class (Parity Constrained Sort). No search.

Beautiful Permutation

O(n)
The ask
Print any permutation of 1..n in which no two neighbours differ by exactly 1, or NO SOLUTION if none exists.
find p ∈ Sₙ with |pₖ − pₖ₊₁| ≠ 1 for all i
Key observations
  1. Two values of the same parity differ by at least 2 — so any ordering within one parity class is already legal.
  2. Print the evens as one run and the odds as another, and there is exactly one adjacency left to police: the junction between the runs.
  3. Evens ascending then odds ascending puts the largest even next to 1; that gap is ≥ 3 as soon as n ≥ 4.
  4. Only n = 2 and n = 3 are impossible — small enough to exhaust by hand (2 and 6 arrangements).
  5. n = 1 looks like an edge case but is trivially fine: there is no adjacent pair to violate anything.
Brute force → why it dies
naiveGenerate permutations of 1..n and test each for an adjacent difference of 1.
cost O(n! · n).
dies at n ≤ 10⁶ → hopeless; already dead at n = 12 (4.8·10⁸ permutations).
therefore Stop searching and construct. Two counting loops, no array stored at all — O(n) time, O(1) state beyond the output.
Diagram
Implementation

The whole solution is two for loops stepping by 2, one starting at 2 and one starting at 1 — no array, no permutation object. The only branch is the hard-coded n == 2 || n == 3 guard, which is a proved fact about those two inputs rather than a generic small-n special case: n == 1 deliberately falls through to the construction and prints 1.

arrays/Beautiful_Permutation.cppverbatim
// Problem: Beautiful Permutation
// Link: CSES 1070
// Pattern: split by parity — evens ascending then odds ascending, so within
// each half consecutive prints differ by 2, and the halves' boundary values
// (largest even, 1) are far apart
// Time: O(n)  Space: O(n) for output buffer
//
// Permutation of 1..n with no adjacent elements differing by exactly 1.
// Print any valid one, or "NO SOLUTION" if none exists.
//
// Example:
//     5 -> 4 2 5 3 1   (any valid beautiful permutation accepted)

#include <iostream>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    if (n == 2 || n == 3) {
        cout << "NO SOLUTION\n";
        return 0;
    }

    for (int i = 2; i <= n; i += 2) cout << i << ' ';
    for (int i = 1; i <= n; i += 2) cout << i << ' ';
    cout << '\n';

    return 0;
}
Gotchan == 1 is not impossible — only n == 2 and n == 3 are, verified by exhausting every arrangement. Getting the guard to n < 4 is the natural wrong move and fails the single-element case.
Recognize"construct a permutation avoiding an adjacent difference of exactly 1" → split by parity, each half is internally safe, check the one junction.

Parity Constrained Sort

O(n log n)
The ask
Only two elements of the same parity may be swapped, any number of times. Produce the arrangement closest to non-decreasing that those swaps can reach.
positions keep their parity class; sort the multiset of values inside each class ascending and write it back in place
Key observations
  1. A swap never changes a position's parity — the set of even positions and the set of odd positions is fixed input data, not a choice.
  2. Within one class every permutation is reachable, so sorting that class ascending removes every inversion inside it.
  3. Inversions across classes cannot be touched by any legal move, so they are the same whatever you do — per-class sorting is therefore optimal, not just good.
  4. The two classes never need to be compared against each other, so there is nothing to merge: the output slot order comes from the original array.
  5. Pass 2 can re-read a[i] % 2 off the array it is overwriting, because the value being written has the same parity as the one it replaces.
Brute force → why it dies
naiveBubble-sort using only legal swaps, or search the reachable arrangements.
cost O(n²) for the bubble; O(k!) for the search.
dies atThe input is T test cases, so the quadratic is paid per case — at N = 10⁵ that is 10¹⁰ swaps for a single case.
therefore Bucket by parity, sort each bucket, refill with two cursors — O(N log N) per case, O(N) space.
Diagram
Implementation

Two passes over the same array and no index bookkeeping: pass 1 pushes each value into evens or odds, pass 2 re-tests a[i] % 2 to decide which bucket's cursor (ei / oi) supplies the replacement. The line that looks unsafe — if (a[i] % 2 == 0) a[i] = evens[ei++]; reading the array it is overwriting — is fine because the incoming value always has the same parity as the outgoing one. An all-even or all-odd array needs no special case: one bucket just stays empty and its cursor is never advanced.

arrays/Parity_Constrained_Sort.cppverbatim
// Problem: Parity-Constrained Sort (Boys/Girls Line)
// Pattern: split by parity, sort each group independently, re-merge on a
//          second pass keyed on the same parity check (no stored indices)
// Time: O(N log N) per test case  Space: O(N)
//
// T test cases. Each has N integers. Only same-parity elements may be
// swapped with each other (evens with evens, odds with odds). Output the
// permutation closest to fully non-decreasing achievable under that
// constraint. Multiple answers accepted if tied.
//
// Example:
//     [2,3,9,1,2,7] -> [2,1,3,7,2,9]
//         [4,2,8]       -> [2,4,8]

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int t; cin >> t;
    while (t--) {
        int n; cin >> n;
        vector<int> a(n);
        vector<int> evens, odds;
        for (int i = 0; i < n; i++) {
            cin >> a[i];
            if (a[i] % 2 == 0) evens.push_back(a[i]);
            else odds.push_back(a[i]);
        }
        sort(evens.begin(), evens.end());
        sort(odds.begin(), odds.end());

        int ei = 0, oi = 0;
        for (int i = 0; i < n; i++) {
            if (a[i] % 2 == 0) a[i] = evens[ei++];
            else a[i] = odds[oi++];
        }

        for (int i = 0; i < n; i++) cout << a[i] << ' ';
        cout << '\n';
    }
    return 0;
}
GotchaStoring the even/odd positions in extra vectors is the reflex and it is wasted work — the parity test is one modulo, cheaper than the bookkeeping. Don't try to merge the buckets by value either: the slot order is dictated by the input, not by comparison.
Recognize"swaps allowed only between elements sharing some predicate" → positions per class are frozen, sort within each class, cross-class inversions are unavoidable and ignorable.

3 · Position-array incremental invariant

Invert the array into pos[value] = index and a question about sweep order becomes n−1 independent one-line comparisons. The first problem sums them once; the second keeps that same sum alive under updates by re-evaluating only the handful of comparisons a change can reach.

Collecting Numbers

O(n)
The ask
The array is a permutation of 1..n. Each round sweeps left to right collecting 1, 2, 3, … in order, taking whatever lies ahead of the current cursor. Count the rounds needed to collect everything.
rounds = 1 + #{ i ∈ [2, n] : pos[i] < pos[i−1] }
Key observations
  1. Only consecutive values interact: after taking i−1 the sweep is at pos[i−1] and can still take i iff i lies to its right.
  2. So i and i−1 share a round iff pos[i−1] < pos[i]; otherwise a new round is forced. Call that a break.
  3. Breaks are independent — each costs exactly one extra round, and one break never creates or cancels another. The answer is a plain sum.
  4. Round 1 is free (value 1 is always collected), which is the +1 seed.
  5. pos[] can be filled while reading, so nothing but the inverse permutation is ever stored.
Brute force → why it dies
naiveSimulate: sweep the array, collect what you can, repeat until everything is gone.
cost O(n) per round, up to n rounds → O(n²).
dies at n ≤ 2·10⁵, and a reversed array needs n rounds → 4·10¹⁰ steps.
therefore Build pos[] and count adjacent-value inversions in one pass — O(n) time, O(n) space.
Diagram
Implementation

The read loop never stores the array — it stores the inverse, pos[x] = i, with i running from 1, so pos holds 1-based indices throughout. The counting loop then reads pos in value order, which is why rounds starts at 1 and the loop starts at i = 2: there are only n−1 adjacent pairs to test.

arrays/Collecting_Numbers.cppverbatim
// Problem: Collecting Numbers
// Link: CSES 2216
// Pattern: position array, count rounds by adjacency breaks
// Time: O(n)  Space: O(n)
//
// Repeatedly sweep left-to-right, each round collecting numbers in
// increasing order as far as the sweep gets them contiguously. Count rounds
// needed to collect 1..n.
//
// Example:
//     4 2 1 5 3 -> 3

#include <iostream>
#include <vector>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    vector<int> pos(n + 1);
    for (int i = 1; i <= n; i++) {
        int x;
        cin >> x;
        pos[x] = i;
    }

    int rounds = 1;
    for (int i = 2; i <= n; i++) {
        if (pos[i] < pos[i - 1]) rounds++;
    }

    cout << rounds << '\n';
    return 0;
}
GotchaThe comparison is on values indexed by value (pos[i] < pos[i−1]), not on the array in index order. Scanning a[] and comparing neighbours answers a different question entirely.
Recognize"how many left-to-right passes to collect values in increasing order" → build pos[], count the places where it steps down.

Collecting Numbers II

O((n+m) log n)
The ask
Same round count as Collecting Numbers, but m swaps of two array positions arrive one at a time and the answer must be printed after each.
maintain breaks = 1 + ∑ₖ₃₂ [pos[i] < pos[i−1]] under swap(pos[u], pos[v])
Key observations
  1. The answer is a sum of n−1 independent indicators. Call indicator k the "edge" for the pair (k−1, k).
  2. A swap of positions a, b changes pos[] for exactly two values: u = x[a] and v = x[b]. The query gives positions, so the values must be looked up first.
  3. Value w appears in only two edges, w and w+1 — so at most 4 indicators can flip per swap, regardless of n.
  4. Those 4 can overlap when u and v are close in value; a set<int> absorbs the duplicates instead of hand-written case analysis.
  5. Subtract each affected edge's old value before the swap, add its new value after. Adding the new value without removing the old one double-counts.
Brute force → why it dies
naiveApply the swap, then re-run Collecting Numbers' full O(n) scan for each query.
cost O(n·m).
dies at n, m ≤ 2·10⁵ → 4·10¹⁰ operations.
therefore Keep the running sum and patch only the ≤4 edges a swap can reach — O(log n) per query from the dedup set, O((n+m) log n) overall.
Diagram
Implementation

isBad(k) is the single indicator, deliberately a lambda so the same expression is used for the initial build and for both sides of every update. Both x[] (position → value) and pos[] (value → position) are maintained, and both are swapped — forgetting swap(x[a], x[b]) corrupts every later query's u, v lookup. The subtract-loop, the two swaps, and the add-loop must stay in that order.

arrays/Collecting_Numbers_II.cppverbatim
// Problem: Collecting Numbers II
// Link: CSES 2217
// Pattern: same break-counting formula as Collecting Numbers I, but
// maintained incrementally — a swap only changes pos[] for the two
// swapped values, so only their up-to-4 adjacent edges can flip status
// Time: O((n + m) log n)  Space: O(n)
//
// Same "rounds" formula as Collecting Numbers I, but m swaps (positions a,
// b) are applied one at a time, reporting rounds after each. Naive O(n) per
// swap is too slow for n, m up to 2e5.
//
// Example:
//     4 2 1 5 3, swaps (2,3) (1,5) (2,3) -> 2 3 4

#include <iostream>
#include <vector>
#include <set>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n, m;
    cin >> n >> m;

    vector<int> x(n + 1), pos(n + 1);
    for (int i = 1; i <= n; i++) {
        cin >> x[i];
        pos[x[i]] = i;
    }

    // edge k means the pair (k-1, k); value w only affects edges k=w and
    // k=w+1, since those are the only pairs w appears in
    auto isBad = [&](int k) {
        return pos[k] < pos[k - 1] ? 1 : 0;
    };

    long long breaks = 1;
    for (int k = 2; k <= n; k++) breaks += isBad(k);

    for (int q = 0; q < m; q++) {
        int a, b;
        cin >> a >> b;
        int u = x[a], v = x[b];

        set<int> edges;
        for (int w : {u, v}) {
            if (w >= 2) edges.insert(w);
            if (w + 1 <= n) edges.insert(w + 1);
        }

        for (int k : edges) breaks -= isBad(k);

        swap(pos[u], pos[v]);
        swap(x[a], x[b]);

        for (int k : edges) breaks += isBad(k);

        cout << breaks  << '\n';
    }

    return 0;
}
Gotchaa and b in a query are array positions, not values — the values that move are u = x[a], v = x[b], and they must be read before the swap. The set is not decoration: when u and v differ by 1 the candidate lists overlap, and counting a shared edge twice desynchronises breaks permanently.
Recognize"a derived count, plus point updates, report after each" → find the fixed-size neighbourhood of conditions one update can reach, subtract old, apply, add new.

4 · Per-value frequency counting

Position is irrelevant here. Both problems reduce the array to "how often does each value occur" and then answer from that table alone — a run count after sorting, or a product over the frequencies. If a sliding window feels natural, the contiguity question has not been asked yet.

Distinct Values

O(n log n)
The ask
Count how many different values appear in a list of n integers.
answer = |{ x₀, x₁, …, xₙ₋₁ }|
Key observations
  1. Sorting makes equal values adjacent, so "have I seen this before?" becomes the local test x[i] != x[i−1].
  2. The sorted array is a sequence of runs; the answer is the number of runs = 1 + the number of adjacent-unequal pairs.
  3. The n > 0 guard on the seed is the only edge case — an empty list has 0 runs, not 1.
  4. A hash set is expected O(n) but not guaranteed: CSES ships an anti-hash test that collapses default integer hashing into a single bucket.
  5. Sorting is comparison-based, so no input can degrade it — the same O(n log n) for every test.
Brute force → why it dies
naiveFor each i, scan x[0..i−1] for an earlier copy; or use unordered_set.
cost O(n²) for the scan; O(n) expected but O(n²) worst case for the hash set.
dies at n ≤ 2·10⁵ → 4·10¹⁰. The unordered_set version actually TLE'd here on CSES's final (anti-hash) test.
therefore sort + adjacent-run scan — O(n log n), worst case, immune to adversarial input.
Diagram
Implementation

Ten lines and no container beyond the input vector. The seed int distinct = n > 0 ? 1 : 0; carries the "first run is free" idea and the empty-input case at once; the loop then adds a run per boundary. Keeping the header comment's note about the unordered_set TLE is deliberate — the choice of sort here is a correctness-under-judge decision, not a stylistic one.

// Problem: Distinct Values
// Link: CSES 1621
// Pattern: sort, count runs of equal adjacent values
// Time: O(n log n)  Space: O(n)
//
// unordered_set with the default hash is vulnerable to CSES's anti-hash
// test (collisions force O(n) per op) -> TLE. Sort is immune to that.
//
// Count distinct values in a list of n integers.
//
// Example:
//     2 3 2 2 3 -> 2

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    vector<int> x(n);
    for (int i = 0; i < n; i++) cin >> x[i];

    sort(x.begin(), x.end());

    int distinct = n > 0 ? 1 : 0;
    for (int i = 1; i < n; i++) {
        if (x[i] != x[i - 1]) distinct++;
    }

    cout << distinct << '\n';
    return 0;
}
Gotchaunordered_set<int> is the obvious answer and it TLEs on CSES — the default integer hash is predictable, so one crafted test forces every key into one bucket and every insert to O(n). Sort, or an ordered container, or a custom hash; never the default.
Recognize"count distinct elements, on a judge" → sort and count adjacent-unequal pairs, not a hash set.

Distinct Subsequences

O(n log n)
The ask
Count the non-empty subsequences (order preserved, contiguity not required) in which no value repeats, modulo 10⁹+7.
answer = ( Πₖ (freq[v] + 1) ) − 1 (mod 10⁹+7)
Key observations
  1. Contiguity is irrelevant, so this is not the sliding-window "distinct subarrays" problem despite the name — there is no window here at all.
  2. A valid subsequence uses each value at most once, so it is fully described by one choice per distinct value.
  3. A value with frequency f has exactly f+1 mutually exclusive options: skip it, or take exactly one of its f occurrences.
  4. Not 2ⁿ — that treats the occurrences as independent bits and permits two copies of the same value in one subsequence.
  5. Choices for different values are independent, so the count is the product; the all-skip choice is the empty subsequence, hence the final −1.
Brute force → why it dies
naiveEnumerate all 2ⁿ subsequences and test each for a repeated value.
cost O(2ⁿ · n).
dies at n ≤ 2·10⁵ → 2⁵⁰⁰⁰⁰⁰ — dead by n = 40.
therefore Count per distinct value instead of per subsequence: one frequency map, one product pass — O(n log n) for the map.
Diagram
Implementation

The array is never stored — values go straight into map<int, ll> freq as they are read, which also handles values up to 10⁹ without any coordinate compression. The product runs over f + 1, not f, and mcorr is applied exactly once at the end: msub can return a negative residue, and correcting after every operation instead of once is the usual way this template gets misused.

arrays/Distinct_Subsequences.cppverbatim
// Problem: Distinct Subsequences
// Link: CSES 2429
// Pattern: per-value option counting — a value with frequency f has (f+1)
// independent options (exclude, or include one of its f occurrences);
// multiply across distinct values, subtract 1 for the empty subsequence
// Time: O(n log n)  Space: O(n)
//
// Count subsequences (not necessarily contiguous) where every element is
// distinct, modulo 1e9+7.
//
// Example:
//     1 2 1 3 -> 11

#include <iostream>
#include <map>
using namespace std;

typedef long long ll;
const ll MOD = 1000000007;

ll mmul(ll a, ll b) { return (a % MOD * (b % MOD)) % MOD; }
ll msub(ll a, ll b) { return (a % MOD - b % MOD) % MOD; }
ll mcorr(ll a) { return (a % MOD + MOD) % MOD; }

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    map<int, ll> freq;
    for (int i = 0; i < n; i++) {
        int v;
        cin >> v;
        freq[v]++;
    }

    ll ans = 1;
    for (auto& [val, f] : freq) {
        ans = mmul(ans, f + 1);
    }

    ans = mcorr(msub(ans, 1));
    cout << ans << '\n';
    return 0;
}
GotchaThe per-value option count is f+1, never 2ⁿ — occurrences of one value are alternatives, not independent switches. And the product counts the empty subsequence, so the −1 is part of the formula, not a fencepost fix.
Recognize"count subsequences with all elements distinct, contiguity not required" → per-value (f+1) options, multiply, subtract the empty one.

5 · Monotonic stack

The one family here that keeps a list of running state rather than a scalar. It applies when an element, once passed, can be proved useless to every future element — then the survivors form a monotone stack and each index is pushed and popped at most once.

Nearest Smaller Values

O(n)
The ask
For every position, report the nearest position to its left holding a strictly smaller value, or 0 if there is none.
ansₖ = max { j < i : x₃ < xₖ }, else 0
Key observations
  1. If j < i and x₃ ≥ xₖ, then j can never be the answer for anything after i: i is both nearer and no larger. j is dead.
  2. So the only live candidates, bottom to top, are strictly increasing in value — a monotonic stack of indices.
  3. The answer for i is whatever is left on top after popping everything ≥ xₖ; an empty stack means no smaller value exists.
  4. The pop test is ≥, not > — an equal value is not smaller, so it must also go.
  5. Every index is pushed once and popped at most once, so the inner while costs O(n) in total, not per element.
Brute force → why it dies
naiveFor each i, walk left until a smaller value appears.
cost O(n²) — a strictly decreasing array makes every walk run to the front.
dies at n ≤ 2·10⁵ → 2·10¹⁰ steps on that input.
therefore Keep the live candidates on a stack and discard dominated indices permanently — O(n) amortised, O(n) space.
Diagram
Implementation

This file is the CSES/CPH shape — full macro block, no comments, output printed inside the scan rather than buffered. The array is 1-indexed (v(n + 1), loop from 1), which is what makes the empty-stack case print 0 for free: index 0 is never pushed, so "no candidate" and "index 0" can never be confused. The stack holds indices, and s.top() is printed directly because the index is what the problem asks for; the values are only ever reached through v[s.top()].
