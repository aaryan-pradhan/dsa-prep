The Ledger · Arrays

Sort + Greedy

Nine problems where the whole solution is sort, then take one pass. Sorting is never the answer here — it is what makes a local rule safe: once the array is ordered, the extreme element can be resolved immediately, a failed comparison can never be rescued by a later element, and an adjacent-swap argument becomes a total order. Reach for this page when an optimisation problem has no visible structure but a single comparison between two elements decides which of them should come first.

Recognition rules

The judgment calls that separate these problems from each other. Every rule must be demonstrated by at least two entries on this page.

1

Two pointers come in two shapes. Converging (i=0, j=n−1) when pairing elements within one array — Ferris Wheel, and the inner loop of Sum of Three Values. Parallel (both start at 0) when matching between two arrays — Apartments. Ask "am I pairing a list with itself, or with another list?" before choosing.

2

Sorting is free only when positions don't matter. Ferris Wheel and Stick Lengths print a number, so the array is sorted in place. Sum of Three Values must print original 1-based positions, so the index rides along inside pair<value,index> and the output reads v[i].sc, never the loop counter. Check the output format before typing sort.

3

"Does some X fit?" is not "can all X be matched?" — a resource used once must be consumed. Apartments cannot binary-search each applicant independently (two applicants would claim the same flat); Sum of Four Values needs the explicit a!=i && a!=j && b!=i && b!=j guard because the stored pair may reuse an index it already spent.

4

When the objective is ∑ position × value, the sort direction falls out of an adjacent swap. Reducing Dishes maximises, so large values must take large multipliers → ascending. Tasks and Deadlines minimises ∑(n−k+1)·aₖ, so small values take large multipliers → also ascending, but for the opposite reason. Write the two-element comparison first; the order is whatever it says.

5

Before sorting, check whether a closed-form bound already answers it. Reading Books is max(∑t, 2·t_max) in one unsorted pass — two lower bounds that happen to be jointly achievable. Stick Lengths only needs the sorted order to locate the median (an nth_element would do), and Missing Coin Sum only needs it to justify breaking early. Sorting is the scaffold for the proof more often than it is the computation.

6

Answer width, every time: 2·10⁵ values of 10⁹ is 2·10¹⁴ — Stick Lengths and Reading Books both overflow int on the accumulator alone, and Tasks and Deadlines reaches ~2·10¹⁶ because its sum is of prefix sums. Only Ferris Wheel's and Apartments' answers (counts bounded by n) actually fit in 32 bits.

1 · Sort + two-pointer greedy matching

Sort, then sweep with one pointer per end (or one per array) instead of testing every element against every other. What makes it work is always the same: after sorting, the element at a pointer is the extreme unresolved one, and its fate is decided this step — either it is matched, or it can be discarded forever. Each step advances a pointer, so the sweep is linear and the sort dominates.

Ferris Wheel

O(n log n)
The ask
n children with weights p[0..n−1]. A gondola carries one or two of them and their total weight must not exceed x. Use as few gondolas as possible.
minimise |P| subject to P partitions {0..n−1}, |S| ≤ 2 and ∑ₖ∈ₛ pₖ ≤ x for every S ∈ P
Key observations
  1. The heaviest unmatched child rides this step no matter what — the only open question is whether anyone joins them.
  2. If anyone fits with the heaviest, the lightest fits. So pairing heaviest with lightest is never worse: swapping in the lightest frees a heavier child for a later gondola.
  3. If the lightest does not fit with the heaviest, nobody does — the heaviest rides alone.
  4. Both branches consume the heaviest and cost one gondola → j−− and count++ are unconditional; only i++ depends on the test.
  5. i == j (one child left) needs no special case: the self-test either passes or fails, and one gondola is charged either way.
Brute force → why it dies
naiveEnumerate partitions into gondolas, or rescan the remaining children for the best partner of the current heaviest.
cost O(n²) for the rescan; super-exponential for the partition search.
dies at n ≤ 2·10⁵ → 4·10¹⁰ comparisons for the rescan alone.
therefore Sort once and converge two pointers — O(n log n) total, O(1) extra state, one pass after the sort.
Diagram
Implementation

The loop body is three lines and only the first is conditional. j--; count++; sit outside the if because the heaviest child is resolved either way — the misread is to expect an else branch. The loop condition is i <= j, not i < j, so the final lone child is still charged a gondola.

arrays/Ferris_Wheel.cppverbatim
// Problem: Ferris Wheel
// Link: CSES 1090
// Pattern: sort, two-pointer from both ends — pair lightest with heaviest
// when they fit together, else heaviest rides alone
// Time: O(n log n)  Space: O(1) extra
//
// n children, gondola holds 1 or 2, total weight per gondola <= x. Minimum
// gondolas needed.
//
// Example:
//     7 2 3 9, x=10 -> 3

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    long long x;
    cin >> n >> x;

    vector<long long> p(n);
    for (int i = 0; i < n; i++) cin >> p[i];

    sort(p.begin(), p.end());

    int i = 0, j = n - 1, count = 0;
    while (i <= j) {
        if (p[i] + p[j] <= x) i++;
        j--;
        count++;
    }

    cout << count << '\n';
    return 0;
}
Gotchaj-- and count++ fire on every iteration, pairing or not. Writing if (fits) { i++; j--; count++; } else { j--; count++; } is the same thing spelled twice; writing else j--; and forgetting count++ silently undercounts the solo riders.
Recognize"minimum number of groups of at most two, under a per-group capacity" → sort, converge from both ends, always consume the extreme.

Apartments

O(n log n + m log m)
The ask
n applicants, applicant i accepts any apartment whose size lies in [aᵢ−k, aᵢ+k]; m apartments of fixed size bⱼ. Each applicant gets at most one apartment and each apartment at most one applicant. Maximise the number of matches.
maximise |M| over matchings M ⊆ A × B subject to |bⱼ − aᵢ| ≤ k for every (i,j) ∈ M
Key observations
  1. An apartment is consumed by a match, so "does some apartment fit applicant i" answered per applicant double-counts the same apartment across several applicants.
  2. Sort both sides ascending and give each applicant the smallest apartment that fits: any larger fitting one is better saved for a larger applicant (exchange argument).
  3. bⱼ < aᵢ−k: too small for this applicant, hence too small for every later (larger) applicant → discard the apartment, j++.
  4. bⱼ > aᵢ+k: too big for this applicant, but a later larger applicant may take it → discard the applicant, i++.
  5. Every step advances at least one pointer, so the sweep is O(n+m) and the two sorts dominate.
Brute force → why it dies
naiveFor each applicant, scan every apartment for a free one inside the tolerance window.
cost O(n·m).
dies at n, m ≤ 2·10⁵ → 4·10¹⁰ checks. Replacing the scan with a binary search is faster but wrong: it never marks the apartment as taken.
therefore Sort both arrays and sweep one pointer per side, consuming on a match — O(n log n + m log m), O(1) extra.
Diagram
Implementation

One while with a three-way branch, and the asymmetry between the first two branches is the whole algorithm: a too-small apartment advances j (discarded permanently), a too-big apartment advances i (the apartment survives for a later applicant). Only the third branch advances both. k is read as long long so a[i] - k is evaluated in 64-bit.

arrays/Apartments.cppverbatim
// Problem: Apartments
// Link: CSES 1084
// Pattern: sort both sides, two-pointer greedy sweep
// Time: O(n log n + m log m)  Space: O(1) extra
//
// n applicants each want a size in [a_i - k, a_i + k], m apartments each of
// fixed size. Maximize the number of applicants matched to a distinct
// apartment.
//
// Example:
//     a = 60 45 80 60, b = 30 60 75, k=5 -> 2

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n, m;
    long long k;
    cin >> n >> m >> k;

    vector<long long> a(n), b(m);
    for (int i = 0; i < n; i++) cin >> a[i];
    for (int i = 0; i < m; i++) cin >> b[i];

    sort(a.begin(), a.end());
    sort(b.begin(), b.end());

    int i = 0, j = 0, count = 0;
    while (i < n && j < m) {
        if (b[j] < a[i] - k) j++;
        else if (b[j] > a[i] + k) i++;
        else { count++; i++; j++; }
    }

    cout << count << '\n';
    return 0;
}
GotchaThe two discard branches are not symmetric — getting them the wrong way round (advancing i when the apartment is too small) throws away applicants who could still be housed. Both branches are only valid because both arrays are sorted ascending.
Recognize"match two groups under a per-pair tolerance, each element usable once" → sort both, one pointer each, three-way branch.

2 · Sort + fixed-k value search

Find k elements hitting an exact target, with k a small constant. The move is always to spend nested loops on k−2 of them and solve the remaining 2-sum in better than linear time — by converging pointers on a sorted array, or by a hash/tree map of pair sums. The trap in both is index bookkeeping: the answer is positions, not values, and every position must be distinct.

Sum of Three Values

O(n²)
The ask
Find three distinct positions whose values sum to x, and print those positions (1-based); print IMPOSSIBLE if none exist.
find i < j < k with aᵢ + aⱼ + aₖ = x (n ≤ 5000)
Key observations
  1. Sorting destroys the answer's own output format — so carry the original index with each value: pair<value, index>, sorted on .fr only.
  2. Fix the smallest of the three. What remains is 2-sum for x − aᵢ over the sorted suffix [i+1, n−1].
  3. 2-sum on sorted data is a converging scan: sum < x can only be fixed by raising the low end (l++), sum > x only by lowering the high end (r--). No branch discards a real solution.
  4. Starting l at i+1 makes the three positions distinct by construction — no equality checks needed anywhere.
  5. Values may repeat; nothing in the scan cares, because it compares sums, not values.
Brute force → why it dies
naiveThree nested loops over all index triples.
cost O(n³).
dies at n ≤ 5000 → ~2·10¹⁰ triples (n³/6), far past a 1s limit.
therefore Sort with indices attached, fix one element, collapse the inner two loops into a converging two-pointer scan — O(n²) ≈ 2.5·10⁷.
Diagram
Implementation

v[i].sc = i + 1 is set before the sort — that one line is the whole reason the output survives reordering, and the printed values are v[...].sc, never the loop variables. The comparator sorts on .fr alone, so equal values keep an arbitrary index order, which is harmless. The commented-out block below solve() is the abandoned 2-sum-by-map attempt, left in the file.

Sum of Four Values

O(n² log n)
The ask
Same question one dimension up: four distinct positions summing to x, printed 1-based, or IMPOSSIBLE.
find p < q < r < s with a[p] + a[q] + a[r] + a[s] = x (n ≤ 1000)
Key observations
  1. Split the quadruple into two pairs: 4-sum becomes 2-sum over pair sums. There are only n²/2 pairs.
  2. One stored pair per sum is enough. m[s] is overwritten as the loops run, so it ends up holding the lexicographically largest (i,j) with that sum.
  3. That is exactly what makes overwriting safe: for an answer p<q<r<s, when the outer loop reaches (p,q) the stored pair for x−a[p]−a[q] is ≥ (r,s), so both of its indices exceed q — disjoint, always.
  4. The four-way index check is still needed: an earlier (i,j) can find a matching sum whose stored pair overlaps it, and that candidate must be rejected, not printed.
  5. The array is stored 1-based, so the indices in the map are already the output format.
Brute force → why it dies
naiveFour nested loops over all index quadruples.
cost O(n⁴).
dies at n ≤ 1000 → 10¹² quadruples. (Fixing two and two-pointering the rest is O(n³) = 10⁹ — still too slow.)
therefore Tabulate every pair sum in a map, then scan pairs again looking up the complement — O(n² log n) ≈ 5·10⁵·20, with O(n²) memory.
Diagram
Implementation

Two identical double loops: the first fills m[v[i]+v[j]] = {i,j} for every pair, the second re-walks the same pairs and looks up x − sum. The line that looks like a bug — blindly overwriting m[sum] — is the one observation 3 defends. The map is std::map, not unordered_map: ordered containers are immune to the CSES anti-hash test, and log n on 5·10⁵ entries is affordable.

Sum of Two Values

O(n log n)
The ask
Find two distinct positions whose values sum to x, or IMPOSSIBLE.
find i ≠ j with aᵢ + aⱼ = x
Key observations
  1. For each i the partner value is forced: x − aᵢ.
  2. A map from value to index answers "does the partner exist" in O(log n).
  3. Storing the last index per value handles aᵢ = x/2: the first copy finds the last copy, a different position.
Brute force → why it dies
naiveCheck every pair.
costO(n²)
dies atn ≤ 2·10⁵ → 2·10¹⁰ pairs.
thereforeValue → index map, one lookup per element: O(n log n).
Diagram
Implementation

The map is filled before the search, so later positions are visible from earlier ones. freq[rem] uses operator[], which inserts a 0 for missing values — 0 doubles as "absent" because positions are 1-indexed.

3 · Sort + single-pass greedy

Sort once, then one forward pass carrying a single scalar — the median, the reachable range R, a running total — decides the answer outright. No second pointer, no table. The recurring shape is that the sorted order makes a local test globally conclusive: the first failure is permanent (Missing Coin Sum), or the quantity being compared is the same at every step (Reducing Dishes).

Stick Lengths

O(n log n)
The ask
n sticks of length pᵢ. Cutting or extending a stick by one unit costs one. Make all sticks equal length, as cheaply as possible.
minimise f(t) = ∑ |pᵢ − t| over integer t
Key observations
  1. Sort, then pair smallest with largest. Any t inside [pᵢ, pₙ₋₁₋ᵢ] pays exactly that pair's width; any t outside pays more.
  2. Those intervals are nested, so a single t in the innermost one is simultaneously optimal for every pair — the lower bounds all bind at once.
  3. The innermost interval is the median. p[n/2] lies in it for both parities.
  4. For even n every point of the median range costs the same, so no averaging and no floating point is ever needed.
  5. The mean is the wrong answer — it minimises squared deviation, not absolute.
Brute force → why it dies
naiveTry every candidate target — every stick length, or every value in the range — and sum the deviations.
cost O(n²) over stick lengths; O(n·max p) over the value range.
dies at n ≤ 2·10⁵ → 4·10¹⁰; over the value range pᵢ ≤ 10⁹ it is hopeless. The answer itself reaches ~2·10¹⁴, past int.
therefore The optimum is provably the median — sort, read p[n/2], one summing pass: O(n log n), accumulator in long long.
Diagram
Implementation

Three lines after the sort: take p[n/2], sum abs(p[i] - median), print. median is declared long long so p[i] - median is a 64-bit subtraction and abs resolves to the long long overload — the one line a reader would gloss over, and the one that silently truncates if the type is int.

arrays/Stick_Lengths.cppverbatim
// Problem: Stick Lengths
// Link: CSES 1074
// Pattern: sort, target = median, sum absolute deviations
// Time: O(n log n)  Space: O(n)
//
// Minimum total cost to make all sticks equal length, cost per stick =
// |new - old|.
//
// Example:
//     2 3 1 5 2 -> 5

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    vector<long long> p(n);
    for (int i = 0; i < n; i++) cin >> p[i];

    sort(p.begin(), p.end());
    long long median = p[n / 2];

    long long cost = 0;
    for (int i = 0; i < n; i++) cost += abs(p[i] - median);

    cout << cost << '\n';
    return 0;
}
GotchaMedian, not mean. And no parity special-case: p[n/2] is correct for even n because every point in the median range gives the same cost — averaging the two middle values would only introduce floating point for no gain.
Recognize"make everything equal, cost is the absolute difference" → sort, target the median, sum the deviations.

Missing Coin Sum

O(n log n)
The ask
Given coin values xᵢ, find the smallest positive integer that no subset of the coins sums to.
min { s ≥ 1 : no S ⊆ coins with ∑ S = s }
Key observations
  1. Sort ascending and carry one invariant: after some prefix, the achievable sums are exactly the contiguous range [0, R].
  2. The next coin x keeps it contiguous iff x ≤ R+1; the new range is [0, R+x]. Equality is included — x = R+1 closes the gap exactly.
  3. If x > R+1, then R+1 is unreachable now, and every remaining coin is ≥ x, so it stays unreachable — stop immediately, the answer is R+1.
  4. Running out of coins is the same conclusion: R+1 again, so the print sits outside the loop and covers both exits.
  5. Sorting is what licenses the early stop; without it, a later small coin could still close the gap.
Brute force → why it dies
naiveMark every achievable sum — enumerate subsets, or run a boolean subset-sum DP over [0, ∑x].
cost O(2ⁿ) for subsets, O(n · ∑x) for the DP.
dies at n ≤ 10⁵, xᵢ ≤ 10⁹ → ∑x up to 10¹⁴ DP cells — unstorable, never mind untraversable.
therefore The reachable set is always one interval, so store its right end only — sort plus one scalar R: O(n log n), O(1) beyond the input.
Diagram
Implementation

The loop is a guard and an accumulation, and the answer is printed after it — so the break path and the ran-out-of-coins path share one line of output. The test is strict x[i] > r + 1; the coins are never re-examined and R is the only state.

// Problem: Missing Coin Sum
// Link: CSES 1745
// Pattern: sort ascending, greedily extend the contiguous achievable-sum
// range [0, R]; a coin x extends it iff x <= R+1, else R+1 is the answer
// Time: O(n log n)  Space: O(n)
//
// Smallest positive sum not formable as a subset sum of the given coins.
//
// Example:
//     2 9 1 2 7 -> 6

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    vector<long long> x(n);
    for (int i = 0; i < n; i++) cin >> x[i];

    sort(x.begin(), x.end());

    long long r = 0;
    for (int i = 0; i < n; i++) {
        if (x[i] > r + 1) break;
        r += x[i];
    }

    cout << r + 1 << '\n';
    return 0;
}
Gotchax == r + 1 must extend, not break — using ≥ in the guard reports a gap that is actually reachable. And it must be break, not continue: skipping the offending coin and carrying on would extend R past an already-proven hole.
Recognize"smallest amount you cannot pay / cannot form" → sort ascending, grow a contiguous reachable range, stop at the first coin above R+1.

Reducing Dishes

O(n log n)
The ask
Choose any subset of dishes and any order for them. The dish cooked k-th scores k · aᵢ (satisfaction may be negative). Maximise the total.
maximise ∑ₖ k · aₛ(ₖ) over subsets S and orderings σ
Key observations
  1. For a fixed subset, ascending order is optimal — swapping an out-of-order adjacent pair gains exactly their difference.
  2. So the only remaining choice is which dishes to drop, and dropping is always a prefix of the sorted array: never drop a dish while keeping a smaller one.
  3. Dropping the front shifts every surviving multiplier down by one, so the answer changes by exactly −T, where T is the current total. The dropped value cancels out of that delta entirely.
  4. Therefore the decision depends only on the sign of T: pop while T < 0, stop the moment T ≥ 0.
  5. If T stays negative to the end, the identity drives the answer to 0 — the empty subset, with no clamp written anywhere.
Brute force → why it dies
naiveTry every subset, sort it, score it. Or a take/skip DP over (index, number already cooked).
cost O(2ⁿ · n) for subsets; O(n²) for the DP.
dies at n in the hundreds → 2ⁿ is unreachable at once; the O(n²) table survives but is rebuilt per test case, and the problem is multi-test.
therefore The prefix-drop identity replaces the table entirely — sort, one scoring pass, one popping pass: O(n log n), O(1) beyond the array.
Diagram
Implementation

The weighted sum is computed once for the full array, then the popping loop edits it in place. The order inside the loop matters: ans -= total; uses the total including the element about to leave, and only then does total -= a[start] remove it. Swapping those two lines applies the wrong delta on the very first pop.

arrays/Reducing_Dishes.cppverbatim
// Problem: Reducing Dishes
// Pattern: sort ascending, then pop the smallest from the front while the
//          running total of included elements is negative
// Time: O(N log N)  Space: O(N)
//
// n dishes with satisfaction[i] (can be negative). Chef picks any subset
// (possibly empty/all) and any cooking order; each dish takes 1 time unit.
// If a dish is the k-th one cooked (1-indexed), its like-time coefficient is
// k * satisfaction[i]. Maximize the total sum over the chosen subset+order.
// T test cases.
//
// Example:
//     [-2,-2,0,3,2]    -> 17
//         [-2,0,-2,3]      -> 7
//         [-2,3,-2,0,1,2]  -> 26

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int t; cin >> t;
    while (t--) {
        int n; cin >> n;
        vector<long long> a(n);
        for (int i = 0; i < n; i++) cin >> a[i];

        sort(a.begin(), a.end());

        long long ans = 0, total = 0;
        for (int i = 0; i < n; i++) {
            ans += (long long)(i + 1) * a[i];
            total += a[i];
        }

        int start = 0;
        while (start < n && total < 0) {
            ans -= total;
            total -= a[start];
            start++;
        }

        cout << ans << '\n';
    }
    return 0;
}
GotchaKeeping everything is not always optimal — [-2,0,-2,3] scores 6 whole but 7 after dropping one -2. And there is no max(ans, 0): the identity already returns 0 when every dish is dropped, so adding a clamp hides a bug rather than fixing one.
Recognize"pick a subset and an order, score is position × value, elements may be dropped" → sort ascending, pop the front while the running total is negative.

Tasks and Deadlines

O(n log n)
The ask
n tasks, task i takes aᵢ time and has deadline dᵢ. Run them one after another from time 0; a task finishing at fᵢ pays dᵢ − fᵢ, negative included. Every task must run. Maximise the total reward.
maximise ∑(dᵢ − fᵢ) = ∑dᵢ − ∑fᵢ ∑dᵢ is fixed ⇒ minimise ∑ fᵢ = ∑ₖ (n − k + 1)·aₖ
Key observations
  1. ∑dᵢ does not depend on the order at all — the deadlines are a constant. Only ∑fᵢ is optimised.
  2. ∑fᵢ is the sum of the duration prefix sums, so the task placed k-th is charged (n−k+1) times.
  3. Swap argument: two adjacent tasks u then v contribute 2aᵤ + aᵥ in one order and aᵤ + 2aᵥ in the other, so putting the shorter first is never worse. Shortest job first, deadlines ignored.
  4. Sorting by deadline (EDF) is the wrong greedy here — it optimises lateness, not the sum of completion times.
  5. The reward is allowed to be negative; there is no filtering and no rejection.
Brute force → why it dies
naiveTry every processing order and score the finishing times.
cost O(n! · n).
dies at n ≤ 2·10⁵ → factorial, and even an O(n²) pairwise-improvement loop is 4·10¹⁰.
therefore The adjacent-swap comparison is a total order on durations alone — sort ascending, prefix-sum, subtract: O(n log n), answer in long long (up to ~2·10¹⁶).
Diagram
Implementation

Deadlines are never stored: d starts life as ∑dᵢ while reading input, then the same variable is decremented by each finishing time and printed as the answer. f[i] += f[i-1] converts the sorted durations into finishing times in place — after that loop f is no longer durations, which is the line to read twice.

Movie Festival

O(n log n)
The ask
Watch the maximum number of non-overlapping movies (one may start exactly when another ends).
max |S|, S ⊆ intervals pairwise disjoint
Key observations
  1. The first movie to take is the one that ends earliest: any optimal schedule can swap its first movie for it without losing anything.
  2. After that choice, the problem repeats on movies starting at or after its end.
  3. Sorted by end, that repetition is a single pass carrying last.
Brute force → why it dies
naiveTry every subset, keep the largest disjoint one.
costO(2ⁿ · n)
dies atn ≤ 2·10⁵.
thereforeSort by end, greedy scan: O(n log n).
Diagram
Implementation

The lambda sorts on .sc (end) only. last starts at 0, below every start time, so the first movie is always taken.

4 · Exchange-argument scheduling

One problem, kept separate because the reasoning is the opposite direction to family 3: instead of sorting and reading off the answer, you write down the lower bounds the schedule must obey, then show a schedule that meets them all at once. When that works the sort disappears entirely and the answer is a closed form.

Reading Books

O(n)
The ask
Two readers must each read all n books; book i takes tᵢ and cannot be read by both at the same time. Reading is uninterrupted, start to end. Minimise the time at which both are finished.
minimise T subject to each reader covers every book and the two readings of any one book never overlap
Key observations
  1. Bound A — work: each reader spends ∑t, so T ≥ ∑t.
  2. Bound B — the longest book is read twice and the two readings cannot overlap, so T ≥ 2·t_max.
  3. Case 2·t_max ≥ ∑t: reader 1 takes the longest book first, reader 2 takes it last; everything else fits in the slack around it → T = 2·t_max.
  4. Case 2·t_max ≤ ∑t: reader 2 reads the same cyclic order shifted by one book, so the two are never on the same book → T = ∑t.
  5. Both bounds are achievable, so the answer is exactly max(∑t, 2·t_max) — no sort, no schedule, no order.
Brute force → why it dies
naiveSearch over the two readers' orderings (and idle gaps) for the earliest joint finish.
cost O((n!)²) orderings, each needing a feasibility check for overlapping readings.
dies at n ≤ 2·10⁵ → there is no search at all at this size; even sorting is more than the problem needs.
therefore Two lower bounds, both constructively achievable — one unsorted pass keeping ∑t and t_max: O(n), O(1), totals in long long.
Diagram
Implementation

One read loop maintaining two scalars, then a single max. No array is stored and nothing is sorted — the input is consumed as it arrives. m is seeded at 0, which is safe only because tᵢ ≥ 1.
