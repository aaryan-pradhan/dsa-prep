The Ledger · Arrays

Range Queries & Binary Search

Two ways of not touching the array element by element. The first five problems precompute a structure over the array — a prefix table or a segment tree — so any range collapses to O(1) or O(log n). The last two never index the array at all: they binary search the answer, and the array only appears inside a monotone feasible(x) predicate. Reach for this page when a problem says "q queries" or "minimise the maximum".

Recognition rules

The judgment calls that separate these problems from each other. Every rule must be demonstrated by at least two entries on this page.

1

Ask two questions in order: does the array change? and does the aggregate have an inverse? Both "no updates" and "invertible" → prefix table, no tree (Static Range Sum Queries, prefix[b] − prefix[a−1]). Either one fails → segment tree. Static Range Minimum Queries is static too, but you cannot subtract a value back out of a min, so it still builds the tree — it just never calls update.

2

Across Static Range Minimum, Dynamic Range Sum, Dynamic Range Minimum and Josephus the build / update / query bodies are byte-identical. Exactly two things vary per problem: the merge body and the identity in node(). Write the scaffold from muscle memory, then think about those two lines only.

3

The identity must be the neutral element of your merge, because query returns a default-constructed node() on no-overlap and that node is merged into the real answer. 0 for the sum trees (Dynamic Range Sum, Josephus), 2e18 for the min trees (Static / Dynamic Range Minimum). A 0 identity in a min tree silently answers 0 for every query that partially overlaps.

4

Default to the segment tree, never a Fenwick tree/BIT. The same sum tree that answers Dynamic Range Sum Queries also runs Josephus Queries' findKth descent with six extra lines — one structure covers point update, range sum, range min and order statistics, so there is one thing to remember under interview pressure instead of two.

5

CSES hands you 1-indexed queries; this repo builds trees 0-indexed over [0, n−1]. Convert once, at the call site — query(1, 0, n-1, a-1, b-1) in both Dynamic entries and in Static Range Minimum, and order[i] + 1 on the way out of Josephus. Never half-convert inside the recursion. Prefix sums are the one exception: Static Range Sum Queries stores prefix[1..n] 1-indexed precisely so the query needs no shifting at all.

6

"Minimise the maximum" (Array Division) or "maximise the minimum" / "shortest time to reach a target" (Factory Machines) → binary search the answer, not the array. Both files have the identical skeleton: a boolean check(mid), then ans = mid; hi = mid - 1 on success and lo = mid + 1 on failure. The array is never sorted and never indexed by the search — it only feeds the predicate.

7

The predicate is where the bugs live, not the search. Array Division needs the v[i] > mid → return false guard, or a single oversized element is silently packed into a block. Factory Machines needs its if (total >= t) return true inside the loop, or ∑ x / kᵢ over 2·10⁵ machines overflows long long. Both times the fix is one line in check.

Segment tree toolkit

The shared scaffolding behind families 1–3, canonical segment tree scaffold. Reproduce this from memory; then change merge and the identity, and nothing else.

node t[4 * MAXN]the 4·n sizing: the recursion is not a perfect binary tree, and a worst-case n (just over a power of two) pushes the largest used index past 2n. 4·n is the safe bound — here MAXN = 200020, so t[800080], a static global, never a vector resized per test.
node()the default constructor is the identity. sum = 0 for a sum tree; mn = INF = 2e18 for a min tree. Nothing else declares it.
merge(a, b)the only genuinely per-problem line. res.sum = a.sum + b.sum or res.mn = min(a.mn, b.mn). Must be associative; must be neutral under node().
build(id, l, r)leaf l == r copies arr[l]; otherwise recurse into [l, mid] / [mid+1, r] and t[id] = merge(children). Called once as build(1, 0, n - 1) — O(n).
update(id, l, r, pos, val)point set, not add: the leaf is overwritten with val, then every ancestor re-merges on the way back up. Out-of-range guard is pos < l || pos > r. O(log n).
query(id, l, r, lq, rq)three cases, in this order: no overlap → return node() (identity); full containment → return t[id]; else merge of both recursive halves. O(log n).
findKth(id, l, r, k)order statistics over a 0/1 "alive" sum tree. Descend from the root: t[2*id].sum >= k → go left with the same k; else go right with k - t[2*id].sum. One path down, no backtracking, O(log n). k is 1-indexed; the returned position is 0-indexed.
children of id2*id and 2*id + 1, root at id = 1. Index 0 is unused — that is what makes the doubling work.
indexingthe tree is built 0-indexed over [0, n-1]; CSES queries arrive 1-indexed. Subtract 1 at the call site: query(1, 0, n-1, a-1, b-1), update(1, 0, n-1, k-1, u).
vs. Fenwick / BITthis repo does not use one. A BIT is shorter but only does invertible prefix aggregates; the segment tree above does point update, range sum, range min and findKth with the same body. One structure, memorised once.

1 · Static range queries

The array is read once and never changes; only the queries vary. That freedom is worth something only when the aggregate is invertible — a sum can be differenced out of a prefix table, a minimum cannot. So these two problems, identical in shape and identical in constraints, land on completely different structures.

Static Range Sum Queries

O(n+q)
The ask
Given a fixed a[1..n] and q pairs (a, b), report ∑ of the elements in each range. Nothing is ever modified.
P[0] = 0, P[i] = P[i−1] + a[i] answer(a, b) = P[b] − P[a−1]
Key observations
  1. Sum is invertible: the range sum is the difference of two prefix sums, so no structure is needed beyond one array.
  2. Build P 1-indexed and size it n+1 — then the query indices need no shifting at all.
  3. P[0] = 0 is the base case, and it is exactly what makes a == 1 work without a special case.
  4. The elements themselves are never needed again, so nothing is stored but P.
  5. 2·10⁵ · 10⁹ overflows int; P is long long.
Brute force → why it dies
naivePer query, loop i = a..b and add.
cost O(nq), one full scan per query.
dies at n, q ≤ 2·10⁵ → 4·10¹⁰ additions. A single sum also reaches 2·10¹⁴, past int.
therefore One prefix pass answers every query by subtraction — O(n + q) time, O(n) space, accumulator in long long.
Diagram
Implementation

The input element x is read into a scalar and folded into prefix[i] immediately — the array itself is never stored, so the only allocation is the n+1-long table. The line worth a second look is prefix[b] - prefix[a - 1]: a is 1-indexed, so a == 1 reads prefix[0], which is the zero written by the vector's constructor.

// Problem: Static Range Sum Queries
// Link: CSES 1646
// Pattern: prefix sums — prefix[i] = sum of first i elements (1-indexed),
// answer for [a,b] is prefix[b] - prefix[a-1]
// Time: O(n + q)  Space: O(n)
//
// Array never changes; answer q range-sum queries.
//
// Example:
//     3 2 4 5 1 1 5 3, query (2,4) -> 11, (5,6) -> 2, (1,8) -> 24, (3,3) -> 4

#include <iostream>
#include <vector>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n, q;
    cin >> n >> q;

    vector<long long> prefix(n + 1, 0);
    for (int i = 1; i <= n; i++) {
        long long x;
        cin >> x;
        prefix[i] = prefix[i - 1] + x;
    }

    for (int i = 0; i < q; i++) {
        int a, b;
        cin >> a >> b;
        cout << prefix[b] - prefix[a - 1] << '\n';
    }

    return 0;
}
GotchaDo not reach for a segment tree here. Static plus invertible collapses to O(1) per query; building a tree is slower, longer, and more to get wrong. Keep prefix as long long — the total reaches 2·10¹⁴.
Recognize"array never changes, answer many range sums" → one prefix pass, answer by subtraction.

Static Range Minimum Queries

O((n+q) log n)
The ask
Same fixed array, same q ranges — report the smallest element of each range instead of the sum.
answer(a, b) = min { a[i] : a ≤ i ≤ b } merge(x, y) = min(x, y), identity = +∞
Key observations
  1. min has no inverse — you cannot un-min a prefix the way you subtract a prefix sum. The prefix trick is dead.
  2. min is associative and idempotent, so any range can be assembled from a handful of precomputed blocks.
  3. A segment tree cuts every range into O(log n) canonical nodes — the same structure used for the dynamic problems, so there is nothing new to memorise.
  4. No updates means update is simply never written; only build and query survive.
  5. The identity is INF = 2e18, not 0: a no-overlap node is merged into the answer, and 0 would win every min.
Brute force → why it dies
naivePer query, scan i = a..b tracking the minimum. Or precompute all O(n²) ranges.
cost O(nq) for the scan; O(n²) memory for the table.
dies at n, q ≤ 2·10⁵ → 4·10¹⁰ comparisons; the full table would be 4·10¹⁰ entries of memory.
therefore Segment tree with a min merge: O(n) build, O(log n) per query, O(n) space.
Diagram
Implementation

The only edits to the standing template are node.mn in place of node.sum, the min merge, and the constructor's INF. The easily-misread line is if (l > rq || r < lq) return node(); — that default node is the +∞ identity, and returning it is how a disjoint subtree declines to affect the answer. n is a file-scope global because build and query take the segment bounds explicitly, not the array length.

arrays/Static_Range_Minimum_Queries.cppverbatim
// Problem: Static Range Minimum Queries
// Link: CSES 1647
// Pattern: segment tree, same template as templates/segment_tree.cpp,
// merge swapped to min (identity = +infinity instead of 0)
// Time: O((n + q) log n)  Space: O(n)
//
// Array never changes; answer q range-minimum queries.
//
// Example:
//     3 2 4 5 1 1 5 3, query (2,4) -> 2, (5,6) -> 1, (1,8) -> 1, (3,3) -> 4

#include <iostream>
using namespace std;
typedef long long ll;

const int MAXN = 200020;
const ll INF = 2e18;

struct node {
    ll mn;
    node() { mn = INF; }
};

node t[4 * MAXN];
ll arr[MAXN];
int n;

node merge(node a, node b) {
    node res;
    res.mn = min(a.mn, b.mn);
    return res;
}

void build(ll id, ll l, ll r) {
    if (l == r) {
        t[id].mn = arr[l];
        return;
    }
    ll mid = (l + r) / 2;
    build(2 * id, l, mid);
    build(2 * id + 1, mid + 1, r);
    t[id] = merge(t[2 * id], t[2 * id + 1]);
}

node query(ll id, ll l, ll r, ll lq, ll rq) {
    if (l > rq || r < lq) return node();
    if (l >= lq && r <= rq) return t[id];
    ll mid = (l + r) / 2;
    node left = query(2 * id, l, mid, lq, rq);
    node right = query(2 * id + 1, mid + 1, r, lq, rq);
    return merge(left, right);
}

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int q;
    cin >> n >> q;

    for (int i = 0; i < n; i++) cin >> arr[i];
    build(1, 0, n - 1);

    for (int i = 0; i < q; i++) {
        int a, b;
        cin >> a >> b;
        cout << query(1, 0, n - 1, a - 1, b - 1).mn << '\n';
    }

    return 0;
}
Gotcha"Static" does not mean "no tree" — that shortcut only exists for invertible aggregates. And the identity must be +∞: leaving the sum tree's node() { sum = 0; } in place makes every partially-overlapping query answer 0, which passes the sample and fails everything else.
Recognize"many range min/max queries, array fixed" → segment tree with the matching merge, build once, no update.

2 · Dynamic range queries

Point updates arrive interleaved with the queries, so nothing precomputed over whole prefixes survives. The segment tree is the answer to both, and the two files differ by three lines — the field name, the merge, and the identity. Read them as one problem solved twice.

Dynamic Range Sum Queries

O((n+q) log n)
The ask
q operations on a[1..n], in any order: set one position to a new value, or report the sum of a range.
type 1 k u : a[k] ← u type 2 a b : report ∑ a[i], a ≤ i ≤ b
Key observations
  1. A prefix table is global: changing a[k] invalidates every P[i] with i ≥ k. That is O(n) per update.
  2. A segment tree is local: position k appears in exactly the log n nodes on its root-to-leaf path, and nowhere else.
  3. So an update is one downward walk plus one re-merge per ancestor on the way back up.
  4. The update sets the value, it does not add to it — the leaf is overwritten, no delta is computed.
  5. Merge is + and the identity is 0: the unmodified template.
Brute force → why it dies
naiveKeep the prefix table and rebuild it after each update (or drop it and scan a..b per query).
cost O(n) per operation → O(nq).
dies at n, q ≤ 2·10⁵ → 4·10¹⁰ operations, and the update mix is adversarial — every update triggers a full rebuild.
therefore Segment tree, sum merge: O(log n) per update and per query → O((n + q) log n).
Diagram
Implementation

This is the canonical segment tree with no adaptation at all — only main is new, dispatching on the operation type. In update both recursive calls are always issued; the one whose segment excludes pos returns on its first line, which is what keeps the walk O(log n) despite looking like a full traversal. The re-merge sits after both calls, so a node is recomputed only once its children are final.

Dynamic Range Minimum Queries

O((n+q) log n)
The ask
The previous problem with one word changed: report the minimum of the range instead of its sum.
type 1 k u : a[k] ← u type 2 a b : report min a[i], a ≤ i ≤ b
Key observations
  1. Nothing new: this is Static Range Minimum's merge plus Dynamic Range Sum's update. Recognising that is the solution.
  2. The parent is recomputed as min of both children, not patched — raising a value can make the parent take the sibling's value instead.
  3. That is why a Fenwick tree does not cover this case while the segment tree does: no inverse, no delta, no prefix trick.
  4. Identity stays INF = 2e18, and INF must exceed any legal answer so it never wins a real query.
Brute force → why it dies
naiveScan a..b per query; apply updates directly to the array.
cost O(1) update but O(n) query → O(nq).
dies at n, q ≤ 2·10⁵ → 4·10¹⁰ comparisons. No prefix escape exists, because min has no inverse.
therefore The same tree again, merge swapped to min and identity to +∞ → O((n + q) log n).
Diagram
Implementation

Diff this against the previous file and only sum→mn, +→min and 0→INF change; main is identical except for the field it prints. INF is 2e18 as a ll constant — comfortably above any input value, and never added to anything, so it cannot overflow the way a sentinel in a sum tree would.

3 · Order statistics on a segment tree

The tree stops being a range-aggregate structure and becomes a searchable index. Store 1 for alive and 0 for removed; then node.sum is a survivor count, and one extra descent turns "which element has rank k right now?" into O(log n). Any repeated remove-by-rank problem lands here.

Josephus Queries

O(n log n)
The ask
n children stand in a circle. Repeatedly skip k survivors and remove the next one. Print the order in which they leave.
rem = survivors, idx = rank just after the last removal nextRank = (idx + k) mod rem + 1 remove findKth(nextRank); idx ← nextRank − 1; rem ← rem − 1
Key observations
  1. Work in ranks among survivors, not positions. Ranks stay dense 1..rem after every removal; positions do not.
  2. In rank space the step is pure arithmetic: (idx + k) % rem + 1. The % rem collapses every lap, so k up to 10⁹ costs nothing.
  3. Removing rank r shifts everyone after it down by one, so the survivor now standing "just after" the gap is again rank r — hence idx = nextRank − 1 feeding the next +1.
  4. Rank → position is the only hard step, and a sum tree over 0/1 alive markers does it: descend, going left while the left child holds at least k survivors.
  5. Removal is a point update to 0 — the same update as the dynamic problems, no new code.
Brute force → why it dies
naiveCircular list or vector: walk k mod rem links each round and erase the node.
cost O(n) per removal — the walk is up to a full lap, and vector::erase is linear anyway → O(n²).
dies at n ≤ 2·10⁵ → 4·10¹⁰ link steps, with k ≤ 10⁹ making every round a worst case.
therefore Sum tree over alive markers plus a findKth descent: O(log n) per removal → O(n log n) total.
Diagram
Implementation

Everything above main is the standing sum tree plus the six-line findKth. The line that repays a second read is ll nextRank = (idx + k) % rem + 1; — idx is a rank, rem is the count before this removal, and the +1 converts a 0-based offset into the 1-based k that findKth expects. Positions are 0-indexed throughout and only become 1-indexed at the final order[i] + 1 print.

// Problem: Josephus Queries (children in a circle)
// Link: CSES 2163
// Pattern: segment tree order-statistics query — find the k-th alive
// element by rank in O(log n), instead of O(n) list simulation
// Time: O(n log n)  Space: O(n)
//
// n children in a circle, indices 1..n. Repeatedly skip k, remove the next
// child. Print the removal order. n up to 2e5, k up to 1e9.
//
// Example:
//     n=7, k=2 -> 3 6 2 7 5 1 4

#include <iostream>
#include <vector>
using namespace std;
typedef long long ll;

const int MAXN = 200020;

struct node {
    ll sum;
    node() { sum = 0; }
};

node t[4 * MAXN];
ll arr[MAXN];
int n;

node merge(node a, node b) {
    node res;
    res.sum = a.sum + b.sum;
    return res;
}

void build(ll id, ll l, ll r) {
    if (l == r) {
        t[id].sum = arr[l];
        return;
    }
    ll mid = (l + r) / 2;
    build(2 * id, l, mid);
    build(2 * id + 1, mid + 1, r);
    t[id] = merge(t[2 * id], t[2 * id + 1]);
}

void update(ll id, ll l, ll r, ll pos, ll val) {
    if (pos < l || pos > r) return;
    if (l == r) {
        t[id].sum = val;
        return;
    }
    ll mid = (l + r) / 2;
    update(2 * id, l, mid, pos, val);
    update(2 * id + 1, mid + 1, r, pos, val);
    t[id] = merge(t[2 * id], t[2 * id + 1]);
}

// 0-indexed position of the k-th alive element (1-indexed k).
ll findKth(ll id, ll l, ll r, ll k) {
    if (l == r) return l;
    ll mid = (l + r) / 2;
    if (t[2 * id].sum >= k) return findKth(2 * id, l, mid, k);
    return findKth(2 * id + 1, mid + 1, r, k - t[2 * id].sum);
}

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    ll k;
    cin >> n >> k;

    for (int i = 0; i < n; i++) arr[i] = 1;
    build(1, 0, n - 1);

    vector<ll> order(n);
    ll idx = 0;
    int rem = n;
    for (int step = 0; step < n; step++) {
        ll nextRank = (idx + k) % rem + 1;
        ll removed = findKth(1, 0, n - 1, nextRank);
        order[step] = removed;

        update(1, 0, n - 1, removed, 0);
        idx = nextRank - 1;
        rem--;
    }

    for (int i = 0; i < n; i++) cout << order[i] + 1 << (i + 1 < n ? ' ' : '\n');

    return 0;
}
GotchaThe state is a rank, not a position — mixing the two is the whole difficulty. % rem uses the survivor count before the removal, and rem-- happens after. The rank of the next starting point is nextRank - 1, not nextRank, because the removed child's rank is inherited by the survivor behind it.
Recognize"repeatedly delete the k-th remaining element / need the current rank-k item fast" → 0/1 alive segment tree with a findKth descent.

4 · Binary search on the answer

No structure is built over the array at all. The search runs over the answer space — a cap in seconds, a cap on a block sum — and the array only appears inside a boolean feasible(x). The whole method rests on that predicate being monotone: false up to some threshold, true from there on. Find the phrase "minimise the maximum" or "maximise the minimum" and this is the shape.

Array Division

O(n log C)
The ask
Cut a[0..n−1] (all positive) into k contiguous blocks so that the largest block sum is as small as possible. Report that sum.
minimise max₂ ∑ block₂ over contiguous partitions into ≤ k blocks feasible(x) ⇔ greedy blocks under cap x ≤ k answer = min { x : feasible(x) }
Key observations
  1. Guess the answer instead of constructing it: fix a cap x and ask only "can it be done within x?"
  2. feasible is monotone — a looser cap never needs more blocks — so the feasible set is a suffix of the number line and binary search finds its left edge.
  3. For a fixed cap, greedily extending the current block until it would overflow uses the fewest blocks possible, so cnt ≤ k settles feasibility in one pass.
  4. Any single element exceeding x makes x infeasible outright, whatever the block count says.
  5. "Exactly k" and "at most k" agree here: values are positive, so splitting a block further never raises the maximum.
Brute force → why it dies
naiveDP over (prefix length, blocks used): dp[i][j] = min over split p of max(dp[p][j−1], sum(p+1..i)).
cost O(nk) states, O(n) transitions each → O(n²k).
dies at n ≤ 2·10⁵, k ≤ n → 4·10¹⁰ states before a single transition is considered.
therefore Binary search the cap, with an O(n) greedy check → O(n log C), about 60 iterations for C = 10¹⁸.
Diagram
Implementation

check is the whole problem; solve is the textbook lower-bound search (ans = mid; r = mid - 1 on success). cnt starts at 1 because the first block is already open, so it counts blocks, not cuts. The declared return type is ll while the returns are true/false — they convert to 1/0 and the function is used as a boolean, so this is cosmetic, not a bug. r = 1e18 is a loose upper bound; the true ceiling is ∑ xᵢ ≤ 2·10¹⁴.

Factory Machines

O(n log C)
The ask
n machines run in parallel; machine i needs kᵢ seconds per product. Find the least time in which t products in total are finished.
products(x) = ∑ ⌊ x / kᵢ ⌋ (non-decreasing in x) answer = min { x : products(x) ≥ t }
Key observations
  1. "You can freely decide their schedule" is a red herring — a machine never benefits from idling, so in x seconds it makes exactly ⌊ x / kᵢ ⌋.
  2. That makes the machines independent: the total is a plain sum, with nothing to allocate.
  3. products(x) is non-decreasing in x, so "products(x) ≥ t" is monotone — binary search the time.
  4. Upper bound: t · min kᵢ ≤ 10⁹ · 10⁹ = 10¹⁸, which is where hi = 1e18 comes from.
  5. The feasibility sum must be capped as it grows — at x = 10¹⁸ over 2·10⁵ machines it would reach 10²³.
Brute force → why it dies
naiveAdvance time product by product — a heap of next-completion timestamps, popped t times.
cost O(t log n), or O(answer) if ticking second by second.
dies at t ≤ 10⁹ → 10⁹ heap pops; the answer itself reaches 10¹⁸, so a per-second loop is hopeless.
therefore Binary search x with an O(n) feasibility sum → O(n log C), about 2·10⁵ × 60 operations.
Diagram
Implementation

Same skeleton as Array Division: a boolean check, then ans = mid; hi = mid - 1 on success. The load-bearing line is if (total >= t) return true; inside the accumulation loop — it is an overflow guard first and an early exit second, keeping total below t + x ≈ 10¹⁸ instead of letting it run to ∑ x / kᵢ. ans is seeded to -1 and is always overwritten, since hi = 1e18 is feasible for every legal input.
