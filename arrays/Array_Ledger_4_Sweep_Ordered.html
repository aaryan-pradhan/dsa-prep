Sweep & Ordered Set

Every problem here arrives as a list of intervals or a stream of points. Two answers follow. Either you sort once and sweep, carrying one or two scalars past every endpoint — or the structure has to stay sorted while it is edited, and a set/multiset does the work a hand-shifted array cannot. Reach for this page when the input is (start, end) pairs, or when the question is asked again after every insertion.

Recognition rules

The judgment calls that separate these problems from each other. Every rule must be demonstrated by at least two entries on this page.

01

Identical input, different aggregate, different sweep. Restaurant Customers and Union of Painted Bricks both read n pairs (l, r). “How many at once” → split each pair into +1/−1 events and sweep a counter. “How much is covered in total” → sort by l and merge into one open block. Decide which one from the question; the data cannot tell you.

02

When the swept counter returns to its starting value, the answer must be latched mid-sweep. Restaurant Customers' running and Room Allocation's c are both 0 at the last event — every arrival is matched by a departure. Both carry a separate best/k updated inside the loop. Reading the final state gives 0, every time.

03

The comparator's tie-break is the problem's inequality — it is never cosmetic. Room Allocation sorts +1 before −1 at equal time because a departure on day t does not free the room for an arrival on day t. Nested Ranges Check sorts r descending on equal l so the wider range is seen first. Flip either one and the code still compiles, still runs, and is wrong.

04

Use multiset, not set, whenever the stored values are distinct entities that may legitimately collide: Tower of Cubes' tower tops (two towers can share a top height), Traffic Lights' gap lengths (two gaps can share a length). Corollary, in both: remove the one instance that changed with s.erase(s.find(x)), never s.erase(x) — the value form erases every match.

05

Sort once, sweep twice. Nested Ranges Check runs the same sorted array forward with a running max r and backward with a running min r, answering the two symmetric halves of the question; Room Allocation sweeps its event array once to size k and again to assign rooms. A second pass over sorted data is free next to a second data structure.

06

Sentinels and pre-sized pools beat boundary special-cases. Traffic Lights seeds positions with {0, x} so the very first light already has a predecessor and a successor; Room Allocation fills the free pool with all k rooms before assigning any, so an arrival never has to invent one. Both turn an “is it empty?” branch into no branch at all.

07

A running extremum certifies existence, never multiplicity. Nested Ranges Check gets its 0/1 answer from a single scalar per pass, and Union of Painted Bricks' (curL, curR) knows how far the block reaches but not how many segments painted any brick. The moment the question becomes “how many”, one scalar touched once per index cannot exceed 1 and the family needs a Fenwick/segment tree over compressed endpoints instead — which is exactly why Nested_Ranges_Count.cpp is in the excluded box at the foot of this page.

1 · Interval sweep & containment

All three sort the intervals first and then make a single pass carrying one or two scalars — a running count, an open block, or the extreme endpoint seen so far. The input shape is the same every time; what changes is which scalar you carry, and that is chosen by the question. The sort key, and especially its tie-break, is where these problems actually go wrong.

Restaurant Customers

O(n log n)
The ask
n customers, customer i present for the whole closed interval [aᵢ, bᵢ]. What is the largest number present at one instant?
answer = maxₜ |{ i : aᵢ ≤ t ≤ bᵢ }|
Key observations
  1. The count only changes at an endpoint, so the maximum is attained at some aᵢ. Only the 2n endpoints matter, not the 10⁹ instants between them.
  2. Who is inside never matters, only how many — so an interval can be shredded into two independent signed events, aᵢ → +1 and bᵢ → −1, and the pairing forgotten.
  3. Sorted by time, the count at any instant is just the prefix sum of those deltas. One pass, one accumulator.
  4. Every +1 is matched by a −1, so the running total ends at 0. The answer has to be captured during the sweep, never read off the end.
  5. CSES guarantees all 2n times are distinct, so no arrival-vs-departure tie ever arises — which is the only reason the default pair ordering is safe here (see the Gotcha).
Brute force → why it dies
naiveFor each of the 2n candidate instants, scan all n intervals and count the ones covering it.
cost O(n²) time, O(n) space.
dies at n ≤ 2·10⁵ → 4·10¹⁰ interval checks. A per-instant array is worse still: t ≤ 10⁹.
therefore Replace the intervals by 2n signed events and sort them. The scan becomes one prefix sum — O(n log n) time (the sort), O(n) space.
Diagram
Implementation

Events are pair<long long, int>, so the plain sort sorts by time and then by delta with no comparator. The line to read carefully is that one: −1 < +1, so at an equal timestamp a departure would be processed before an arrival. That is the opposite of what Room Allocation needs, and it is only harmless here because the statement guarantees distinct times. best is updated every iteration, not after the loop.

arrays/Restaurant_Customers.cppverbatim
// Problem: Restaurant Customers
// Link: CSES 1619
// Pattern: sweep line — split each interval into +1/-1 events, sort by
// time, track running total and its max
// Time: O(n log n)  Space: O(n)
//
// Given n (arrival, leaving) intervals, find the max number simultaneously
// present.
//
// Example:
//     (5,8) (2,4) (3,9) -> 2

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    vector<pair<long long, int>> events;
    events.reserve(2 * n);
    for (int i = 0; i < n; i++) {
        long long a, b;
        cin >> a >> b;
        events.push_back({a, 1});
        events.push_back({b, -1});
    }

    sort(events.begin(), events.end());

    int running = 0, best = 0;
    for (auto& [time, delta] : events) {
        running += delta;
        best = max(best, running);
    }

    cout << best << '\n';
    return 0;
}
GotchaThe running total is 0 at the last event — capture best inside the loop or the answer is always zero. And the default pair sort orders −1 before +1 on a tie, i.e. it assumes a customer who leaves at t frees the table for one arriving at t. That holds here only because all times are distinct; do not copy this comparator into a problem that allows ties.
Recognize“maximum number of intervals active at the same moment” → shred into ±1 events, sort, prefix-sum, latch the max.

Union of Painted Bricks

O(N log N)
The ask
N days, day i paints every brick in [Lᵢ, Rᵢ]; repainting changes nothing. How many distinct bricks end up painted?
answer = | ⋃ᵢ [Lᵢ, Rᵢ] ∩ ℤ |
Key observations
  1. Brick numbers reach ~10⁹ — the answer must be computed from the N intervals alone, never from a per-brick array.
  2. The union of intervals is a set of disjoint maximal blocks, and sorting by L discovers them strictly left to right.
  3. With the list sorted by L, a new segment either starts inside the open block (l ≤ curR) — extend curR = max(curR, r) — or starts past it, which proves the open block is final.
  4. Endpoints are inclusive brick indices, so a finished block contributes curR − curL + 1, not curR − curL.
  5. The last block has no successor to trigger its flush. It is flushed once more after the loop — that trailing line is not a duplicate.
  6. N · 10⁹ reaches ~10¹⁴: long long for the total.
Brute force → why it dies
naiveA bool painted[] over the bricks, set to true across each interval; or pairwise overlap tests between all segments.
cost O(∑ length) time and O(max coord) space for the array; O(N²) for the pairwise version.
dies at R ≤ 10⁹ → a 10⁹-entry array (~1 GB as bool) that a single interval can also take 10⁹ steps to fill.
therefore Work in interval space, not brick space: sort by L and merge in one pass — O(N log N) time, O(N) space, independent of coordinate size.
Diagram
Implementation

Sorting a vector<pair<ll,ll>> orders by L then R for free, and equal L needs no tie-break here — max(curR, r) picks up the right end whichever of them is processed first. seg[0] seeds the open block before the loop, which is why the loop starts at i = 1. The total += after the loop is the second flush, for the block that never met a segment far enough right to close it.

arrays/Union_Of_Painted_Bricks.cppverbatim
// Problem: Union of Painted Bricks
// Pattern: sort intervals by L, merge overlapping, sum merged lengths
// Time: O(N log N)  Space: O(N)
//
// N days, each day Mantesh paints all bricks in [L_i, R_i] (repaint is a
// no-op). Brick numbers can be up to ~1e9, so a per-brick boolean array
// doesn't fit. Count total distinct bricks painted = size of the union of N
// intervals.
//
// Example:
//     (2,5),(10,10),(4,5),(3,7),(12,14) -> 10

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n; cin >> n;
    vector<pair<long long, long long>> seg(n);
    for (int i = 0; i < n; i++) cin >> seg[i].first >> seg[i].second;

    sort(seg.begin(), seg.end());

    long long total = 0;
    long long curL = seg[0].first, curR = seg[0].second;
    for (int i = 1; i < n; i++) {
        long long l = seg[i].first, r = seg[i].second;
        if (l <= curR) {
            curR = max(curR, r);
        } else {
            total += curR - curL + 1;
            curL = l;
            curR = r;
        }
    }
    total += curR - curL + 1;

    cout << total << '\n';
    return 0;
}
GotchaTwo easy losses. The flush after the loop is mandatory — drop it and the final block vanishes from the total. And the contribution is curR − curL + 1: these are inclusive brick indices, not real-line coordinates, so every block is one brick short without the +1. long long throughout; the total reaches ~10¹⁴.
Recognize“how many distinct positions are covered by these ranges, coordinates too large to mark” → sort by left endpoint, merge into one open block, sum inclusive lengths.

Nested Ranges Check

O(n log n)
The ask
n distinct ranges. For each one, print whether it contains some other range, and whether some other range contains it. Two 0/1 lines, in input order.
[a,b] contains [c,d] ⇔ a ≤ c and d ≤ b containsᵢ = [ ∃j≠i : aᵢ ≤ aⲟ and bⲟ ≤ bᵢ ]
Key observations
  1. Containment is two inequalities. Sorting by l ascending makes the first one free for every earlier element, so only r is left to test.
  2. Forward pass: range i is contained by something earlier iff rᵢ ≤ the largest r seen so far. One scalar replaces the whole prefix.
  3. Backward pass is the mirror image: scanning right to left, every later range already has l ≥ lᵢ, so i contains something iff rᵢ ≥ the smallest r seen so far.
  4. Equal l is the one case where “earlier in the array” stops meaning “starts no later”. Break ties by r descending: the wider range is then placed first, so it is already in maxr when the narrower one is tested, and the narrower one is already in minr when the backward pass reaches the wider one. One sort key serves both passes.
  5. Ranges are guaranteed distinct, so no range is ever its own witness — no i ≠ j guard is needed anywhere.
  6. A scalar answers “does one exist”. It cannot answer “how many” — see rule 07 and the excluded box.
Brute force → why it dies
naiveTest every ordered pair (i, j) against both inequalities.
cost O(n²) time, O(n) space.
dies at n ≤ 2·10⁵ → 4·10¹⁰ pairs against a 1 s limit.
therefore Sort by (l asc, r desc) so one inequality is free, and collapse the other into a running extremum — two linear passes, O(n log n) total from the sort.
Diagram
Implementation

v is vector<pair<pll, ll>>: the range in .fr and its original index in .sc, which is how answers get written back in input order after the sort scrambles it. The one line a reader misreads is the output: ans1 is built by the forward maxr pass and means “is contained by something”, ans2 by the backward minr pass and means “contains something” — and they are printed in the reverse order to which they are computed, ans2 first, because the statement asks for “contains” on line one. minr is seeded from the INF macro, a double 1e18, which is safe only because r ≤ 10⁹.

GotchaThe comparator's second line is return a.fr.sc > b.fr.sc — strictly descending r on equal l. 2 · Heap-backed interval assignment

The sweep still finds the number, but now it also has to hand back an assignment. The textbook shape keeps a min-heap of (departure day, room) and pops it when the next arrival clears the earliest departure. This solution reaches the same O(n log n) from the other side: sweep ±1 events to learn k, then keep the free rooms in a plain stack — once k is fixed, every free room is interchangeable, so the heap's ordering is work nobody reads.

Room Allocation

O(n log n)
The ask
n customers, customer i occupying days [aᵢ, bᵢ]. Two customers may share a room only if the first one's departure is strictly earlier than the second one's arrival. Print the minimum number of rooms and one valid room per customer.
k = maxₜ |{ i : aᵢ ≤ t ≤ bᵢ }| share(i, j) ⇔ bᵢ < aⲟ (strict — not ≤)
Key observations
  1. “Departure strictly earlier than arrival” means the closed intervals must not touch: a room freed on day t is available from day t+1, not day t.
  2. So two customers conflict exactly when their day-intervals overlap, and the answer is the maximum concurrency k — the same ±1 sweep as Restaurant Customers.
  3. k is a lower bound (that many customers are present at once) and it is achievable, because processing events in time order never needs a room beyond the running peak.
  4. Which free room a customer gets is irrelevant. The free rooms need no ordering at all — a stack is enough; no heap, no priority queue.
  5. Sorting +1 before −1 at an equal timestamp encodes the strictness with no extra code: at day t the arrivals grab rooms before that day's departures return any.
  6. The pool is pre-filled with all k rooms, and k came from this very sweep — so rooms.back() can never be called on an empty vector.
Brute force → why it dies
naiveProcess customers in arrival order; for each, scan every room opened so far for one whose last departure is earlier than this arrival, else open a new room.
cost O(n·k), i.e. O(n²) when the intervals nest.
dies at n ≤ 2·10⁵ and k up to n → 4·10¹⁰ room scans.
therefore One sorted event list, swept twice: once to get k, once to assign. The room scan becomes an O(1) pop_back/push_back on a free-room stack — O(n log n) overall, all of it the sort.
Diagram
Implementation

Events are array<ll,3> of {time, ±1, customer index}, and the comparator's second line, return a[1] > b[1], is the entire strictness rule: +1 sorts ahead of −1. The same sorted vector is then swept twice. rooms is filled k, k−1, …, 1 precisely so that back() is room 1 — it is a stack, not a heap, and pop_back/push_back are the whole allocator. Nothing keys on departure order, because nothing needs to.

GotchaThe sharing rule is strict: bᵢ < aⲟ. A room whose guest departs on day t is free for a guest arriving on day t+1, not day t — so at an equal timestamp the arrival must be processed first, which is what return a[1] > b[1] buys. 3 · Ordered-set greedy maintenance

Here the sorted structure is not built once and read — it is edited at every step. Each element arrives, a predecessor/successor lookup finds the one place it interacts with, and one element is removed while one or two are inserted. In every problem here the container must be a multiset, because the values it stores are separate entities that can collide, and the answer is read straight off the container (size(), *rbegin()) rather than accumulated.

Tower of Cubes

O(n log n)
The ask
Cubes c₁ … cₙ arrive in this fixed order. Each is placed on top of an existing tower whose current top is strictly larger, or starts a new tower. Minimise the number of towers.
place c on tower T ⇔ top(T) > c , then top(T) := c minimise |{towers}|
Key observations
  1. A tower's history is irrelevant; only its current top can accept anything. The whole state is the multiset of tops.
  2. Two towers can genuinely have the same top — so multiset, not set.
  3. Among all tops > c, place on the smallest: it is the one least useful to any future cube, and every cube that fits under it also fits under the larger ones. Tightest fit first is the greedy hinge.
  4. “Smallest top strictly greater than c” is exactly upper_bound(c). lower_bound would return a top equal to c, which cannot accept it.
  5. Every cube inserts one value and erases at most one, so the multiset's size grows by one exactly when no tower fits — the final size() is the tower count. Nothing needs counting.
Brute force → why it dies
naiveKeep the tops in a vector; for each cube scan every tower for the tightest fit and overwrite it.
cost O(n · towers) → O(n²) when the input is increasing and every cube starts its own tower.
dies at n ≤ 2·10⁵ → 4·10¹⁰ scans; a sorted vector does not help, since the insert still shifts O(n) elements.
therefore A multiset: upper_bound, erase and insert are each O(log n) and the container re-sorts itself — O(n log n) total.
Diagram
Implementation

Three multiset calls per cube and no bookkeeping at all. tops.erase(it) takes the iterator, which removes exactly that one element — the value overload would remove every top of that height. The insert is outside the if on purpose: both branches end by putting c into the multiset, and the only difference is whether an old top was erased first. The three // this takes O ( log n ) time comments are the author's own.

arrays/Tower_Of_Cubes.cppverbatim
// Problem: Tower of Cubes
// Link: CSES 1073
// Pattern: patience-sorting-style greedy — multiset of tower tops, place
// each cube on the tightest-fitting tower (smallest top strictly > cube)
// Time: O(n log n)  Space: O(n)
//
// Process cubes in given order. Each cube either starts a new tower or goes
// on top of an existing tower whose current top is strictly larger.
// Minimize the number of towers.
//
// Example:
//     3 8 2 1 5 -> 2

#include <iostream>
#include <set>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    cin >> n;

    multiset<int> tops;
    for (int i = 0; i < n; i++) {
        int c;
        cin >> c;
        auto it = tops.upper_bound(c);
        // this takes O ( log n ) time
        if (it != tops.end()) {
            tops.erase(it);
            // this takes O ( log n ) time
        }
        tops.insert(c);
        // this takes O ( log n ) time
    }

    cout << tops.size() << '\n';
    return 0;
}
Gotchaupper_bound, not lower_bound — the rule needs a top strictly greater, and a top equal to c cannot take it. multiset, not set — two towers may share a top. And erase(it) by iterator, never erase(value), which would delete every tower with that top at once.
Recognize“minimum number of piles / towers / sequences, each must stay monotonic, input order is fixed” → multiset of pile tops, tightest-fit placement, answer is size().

Traffic Lights

O(n log n)
The ask
A street spans [0, x]. n lights are added one at a time at distinct positions. After each addition, print the length of the longest stretch with no light.
after each insert: max over consecutive cut points pⲟ₊₁ − pⲟ of the current set ∪ {0, x}
Key observations
  1. The lights cut the street into gaps between consecutive cut points. Adding one light destroys exactly one gap and creates exactly two.
  2. The destroyed gap is the one bracketing p: from its predecessor lo to its successor hi among the current cut points. That is one upper_bound plus one decrement.
  3. Treating 0 and x as cut points from the start means every inserted light has both a predecessor and a successor — no first-light or last-light case.
  4. The maximum gap never grows, but it cannot be kept as a single scalar: when the gap that was the maximum is split, the answer becomes the next largest, which only the full collection knows.
  5. Gap lengths repeat even though positions cannot — so multiset, and the current maximum is *gaps.rbegin() in O(1).
Brute force → why it dies
naiveKeep the positions in a vector; after each insertion re-sort (or rescan) and take the largest adjacent difference.
cost O(n²) for the rescan, O(n² log n) if re-sorting.
dies at n ≤ 2·10⁵ → 4·10¹⁰ differences recomputed, almost all of them unchanged.
therefore Two ordered containers with separate jobs: a set of positions for O(log n) predecessor/successor, and a multiset of lengths for O(1) max — O(n log n) total, O(1) work per query beyond the update.
Diagram
Implementation

positions.upper_bound(p) gives the first cut point strictly above p — hi is read off it before the iterator is stepped back to give lo, which is the one line worth slowing down for. The if (it != positions.begin()) guard can never actually fire: 0 is always in the set and p > 0, so upper_bound is never begin() — it is defensive, not load-bearing. The two containers are updated in lockstep, and the answer is printed straight from *gaps.rbegin() with no separate maximum tracked anywhere.

arrays/Traffic_Lights.cppverbatim
// Problem: Traffic Lights
// Link: CSES 1163
// Pattern: set of boundary positions (with 0, x sentinels) for
// predecessor/successor lookup, multiset of gap lengths for O(1) max
// Time: O(n log n)  Space: O(n)
//
// Street 0..x, lights added one at a time at distinct positions. After
// each addition, print the longest gap with no light.
//
// Example:
//     x=8, lights 3 6 2 -> 5 3 3

#include <iostream>
#include <set>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    long long x;
    int n;
    cin >> x >> n;

    set<long long> positions = {0, x};
    multiset<long long> gaps = {x};

    for (int i = 0; i < n; i++) {
        long long p;
        cin >> p;

        auto it = positions.upper_bound(p);
        // this is the first element > p, so the previous element is the largest <= p

        long long hi = *it ; 
        
        if (it != positions.begin()) {
            it--;
        }

        long long lo = *it;

        gaps.erase(gaps.find(hi - lo));
        // all in O of log n time, since multiset is implemented as a balanced BST
        gaps.insert(p - lo);
        gaps.insert(hi - p);
        positions.insert(p);

        cout << *gaps.rbegin() << ' ';
    }
    cout << '\n';

    return 0;
}
Gotchagaps.erase(gaps.find(hi − lo)) removes one instance; gaps.erase(hi − lo) removes every gap of that length and quietly destroys the answer — two gaps sharing a length is the normal case, not a corner case. Also seed positions with {0, x} and gaps with {x} up front; without the sentinels the first light has no bracketing pair to look up. Note the local is named lo, not prev, because prev collides with std::prev under using namespace std.
Recognize“insert cut points one at a time, report the longest remaining segment after each” → set of positions for predecessor/successor, multiset of lengths for the max.

Concert Tickets

O((n+m) log n)
The ask
Customers arrive in order, each paying at most t. Sell each the most expensive remaining ticket ≤ t, or −1.
Key observations
  1. "Largest value ≤ t" is a predecessor query: upper_bound(t), step back once.
  2. Tickets with equal prices are distinct tickets ⇒ multiset.
  3. Selling removes exactly one copy ⇒ erase by iterator, not by value.
Brute force → why it dies
naiveScan all unsold tickets for each customer.
costO(n·m)
dies atn, m ≤ 2·10⁵ → 4·10¹⁰.
thereforeBalanced BST (multiset) with predecessor + erase: O((n+m) log n).
